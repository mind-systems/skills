# Phase 43 — the unit is fixed for the walk and open for the call

`command-pin-gaps` speaks in the singular everywhere its unit is at stake: "The unit of the walk is one behavior the task claims"; "would the run, holding this task and nothing else, have to invent — and can the task be implemented on the code that exists at all"; and the default mode's own report line closes on "edit the file in place... then report `N closed from source · M blocking · K owned elsewhere`" — "the file," not "the files." Its targeting paragraph is the one place that breaks this: it permits "a named task, phase, or task spec" or "all open `- [ ]` tasks of the roadmap in play... above `---STOP---`" as a single invocation. Nothing anywhere says what the walk does when the named target holds many tasks — once per task with its own finding list, or one undifferentiated pass over everything named.

The reason this is a defect and not an untidiness: the first deciding question is asked under a stated condition — "would the run, holding this task and nothing else, have to invent." Several tasks held in one reading remove that condition. A hole in one task can be closed by context that lives only in another — a shared type, a shared surface, a decision one task made that the next assumes — and the run executing the first task alone will never hold that context, since the condition the question depends on was never actually true for it. The answer the walk returns looks exactly as confident as it would under the true condition, and is not. The skill's own question cannot be answered truthfully in the mode its own targeting permits.

On the empty result, both halves stated and kept apart. `command-pin-gaps` has no statement of yield anywhere, and no applicability gate of any kind: every task that reaches it is walked, and the file's only variability is in what the walk finds, never whether it runs at all. `roadmap-decompose-skeleton` closes its opening paragraph with "It applies to heavy or hazardous tasks and shared type surfaces only — most open tasks pass through untouched" — a claim about which tasks warrant its own skeleton/TDD/concurrency lens, not about a scan's yield. The two are not the same statement, and treating them as parallel — as this phase's own drafted preamble did — is the reading the files refute.

The report shape: default mode ends on "`N closed from source · M blocking · K owned elsewhere`," and `docs/sakshi-harness/skill-cycle.md` describes the identical three groups — "Отчёт считает три группы: закрыто из источника, блокеры, отдано владельцу," literally "The report counts three groups: closed from source, blockers, given to an owner." A clean pass renders as all zeros, mechanically identical to a pass that did not look hard enough, and neither surface tells a reader how to tell the two apart. That is what makes the pressure to find something structural rather than a matter of temperament.

`skill-cycle.md` is the only account of this pass anywhere. It is singular throughout, it never names a phase or a batch as a target, and it never mentions an empty result. On the one point where a doc and the skill could have disagreed — the report shape — they agree. So this phase's divergence is the code against itself, and no document states the unit of invocation or the meaning of a clean pass at all.

Nothing under `docs/` is written. This note is where a finding wanting a doc stops.
