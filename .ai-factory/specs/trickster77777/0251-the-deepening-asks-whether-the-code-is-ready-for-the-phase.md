# Phase 91 — the deepening asks whether the code is ready for the phase

[principles-at-their-moment](../../../docs/philosophy/principles-at-their-moment.md) governs the form: a well-known principle is carried as one question, short enough to be answered on the spot, asked by the skill that is in the middle of the decision and firing on an event, never on style. The principle here is Kent Beck's: make the change easy, then make the easy change. The doc does not state it yet; it lists the principles the family carries and the question each has, and this one has none.

No skill asks what shape the code must have for a phase to land as one change, and whether it has that shape now. When it does not, the question is answered by the pipeline, as stops: plans fail round after round on the same ground. The user's practice then is by hand: delete the phase, insert a preparatory phase before it, decompose that one and land it, and decompose the main phase again. The re-decomposition is not waste; it follows from what a task is written against. A task's now is the code as every open task above it leaves it, so tasks of the main phase written before the preparatory phase lands are written against a code that will not be there.

The idea is to ask the question at the deepening, where the code has already been read, and to let the answer decide the order. When the code is ready, nothing changes. When it is not, a preparation comes first, its behaviour unchanged. Where the preparation's after can be known in advance, a pure move with class, file and method names pinned, it is a task inside the phase and the later tasks are written at once against that after. Only where its after cannot be known in advance is it a phase of its own, the only one decomposed, and the main phase waits undecomposed until it lands. The order of the cycle stays the same: outline, deepening, governing doc, decomposition. The user, on where the question belongs: «дип — реально подходит к этому больше всего».

Where the skills stand against that:
- **`roadmap-outline-deep`** (`src/skills/roadmap-outline-deep/SKILL.md`) reads, at its Step 0, the docs the header and preamble link and the code the phase is about, down to the leaf, and holds that "What is not yet as those docs say is the phase". Its premise is the same: a phase exists "precisely where the docs and the code diverge". Step 1's template for the note is "a short statement, in words, of what is not yet as the docs say", the essence of the phase and what decomposition cuts tasks from. So the code is read and the note says only what differs from the docs; it has no place for the shape the code needs for the change.
- **The same skill's rules** forbid it to "draft, renumber, reorder, or delete phases" and to touch task lines. A preparatory phase placed before the main one is a phase drafted and ordered, so the deepening names the need and does not make the phase, and its rule stays as it is. The agent drafts the preparatory phase through `roadmap-outline`, after the user confirms or during the discussion. The user: «этим занимается агент и может использовать для этого аутлайн скилл. После подтверждения или во время обсуждения».
- **`command-pin-gaps`** asks, of one task and the code it lands in, whether the orchestrator would have to guess; its end toward the code names "an existing shape it must fit that nobody looked at". That is one task's landing, asked after the tasks are written, and it does not ask what a phase needs of the code.
- **`roadmap-decompose-skeleton`** works on a task list that already exists, on the surfaces tasks add; it is a second pass over atomized tasks and does not read a phase's code for readiness.

What the skill says of it is not decided. The phase collects touches, and is decomposed when they settle the form of the question.

**Cases.** Touches collect here, each as the root in a line and the form the repair took.
- **Core's 93.17 series, rescue reports `0040`, `0041` and `0042`** (`.ai-factory/rescue-reports/tradeoxy_core/`). The task filled a throwing shell that catches a pair up after a connect, into a watch loop and a second store that were shaped for the live stream: the loop calls the connect hook only after the first batch of trades, and the store discards every trade below the live seconds' start. Round after round the plans fitted the new behaviour to that shape and each review found the opposite face of one boundary, a fetch bounded by time where the stream and the store are bounded by order. The first report says the guard added for the fifth finding, a timer, "is the sign that the mechanism was the thing to question". What ended it, in the reports, was a rule that ends the catch-up by id and a split in which a plain reader of trade ranges, behind its own interface and with its own spec, is a task of its own and lands first. That is the nearest the series comes to preparation, and it is not the whole of it: the reports do not call the existing loop or store unready, the reader is new behaviour in a unit of its own and not a change to existing code with behaviour unchanged, and the root each report names is the spec's bound. The series is a touch of this phase through the shape it met and the order the repair gave.
- **The user's own practice.** By the user's own account, relayed in the message that opened this phase, he inserts a preparatory phase by hand when a phase will not land as one change: he deletes the phase, puts the preparation before it, decomposes and lands that, and decomposes the main phase again. No file holds a case of it; the practice is what the phase would make the deepening's question.
- **A control, from core 130's message of 2026-10-21, which is in no file here.** The lens was run, at the user's request, on a phase the code had been prepared for, where nothing was expected: core's Phase 88, a candle read that serves history without holes, whose tasks stand in specs `0380`–`0389`, and Phase 92, where the code already had the shape. It found one unready place, and only one: the history read had no single owner, because the registry held it together with the live methods. That place was already named in the phase header and already cut as task 88.2, a move into `CandleHistoryReader` with behaviour unchanged. For every other task the shape existed, named by file and symbol. In the author's readiness report the lens did not push toward invention: the author was tempted to call the private helpers of `ClosedMinutes` a second home needing a merge, and held back, judging that they serve another caller and that the phase does not need them. The floor holds because the question is tied to the phase, is the code ready for this phase, and not to the code at large. A later fact, from the same message: the rescue of core's task 88.6 (report `0044`, a case in [phase 80's note](0226-a-rescue-repairs-to-the-root-and-the-root-may-be-something-to-remove.md)) found that the spec's own clause, "there is one home for the rule", required that merge of the helpers, and it became the preparation 88.6.2. The lens's question was the right one for 88.6, and what the code needed showed itself in the rescue. The user's ruling on it: «я не считаю, что ответ был поспешным. Это поведение агента и не думаю, что мы можем тут что то сделать. Задача наших скилов больше объяснить структуру, в которой развивается проект.. И не ставить заборов или каких то требований, которые агент и так сам делает..» The control gives a refinement, which is in the essence: here the preparation is a task inside the phase and the later tasks were written at once against its after, which is safe because a pure move with its names pinned has an after that is predictable.

**An observation, held for watching and not a rule.** Forcing behaviour into a form that is not ready for it breeds guards: each guard defends the new behaviour against the form it was fitted to, and the next review finds the next place where the two do not meet. The user, when it was named: «ты наконец то сформулировал то, что я чувствовал всю дорогу… предлагаю наблюдать внимательно». The first touch to watch is the timer in the 93.17 series above; whether the same shape recurs elsewhere is what the phase is collecting.

One edge to keep with it: preparation is a change to the existing code with behaviour unchanged. It is never a split that separates a task's tests from the body they test; that split is the trap named in [a contract-task pays only for the unit that holds the hazard](0250-a-contract-task-pays-only-for-the-unit-that-holds-the-hazard.md).

New touches are added as they come.
