# Phase 80 — a rescue makes the task reflect what the system needs

[what-a-task-carries](../../../docs/what-a-task-carries.md) governs what a rescue writes into a spec, because a rescue that repairs a spec writes a spec. It says a task spec holds three parts, "and none of them is a check", and that a spec which also says how to verify "hands the implementer a job that was never the implementer's"; [names-and-reasons-not-laws](../../../docs/names-and-reasons-not-laws.md), in the passage opening "Checks and fences in specs.", records that such specs "came back as plan steps and rounds of review".

Where `src/skills/task-rescue/SKILL.md` stands:
- **Step 3, "Extract root cause".** The report ends with a sentence "stating the missing or wrong constraint in the spec/contract, phrased so that, had it been present, the failure chain would not have occurred", and recurring issues are read as the case where "the description is the only reliable enforcement". The phrase presets the answer's form: the root is always a constraint, so a failure that the spec's own check, fence or census produced is read as a missing constraint, and the repair grows it.
- **Step 3, the categories.** "Specification gap", "Scope overload", "Mechanical error — recurring execution mistakes independent of the task spec" and "Stale implementer session". They say where a failure came from and leave the form of the repair to Step 4.
- **Step 4, "Choose repair depth".** The standard depths preset that form: each begins by repairing the spec — "1. spec — repair task spec + contract line", "2. spec + plan — repair spec + plan .md", "3. spec + plan + code" — and "Depth: spec" in Step 5 opens "Edit the task spec … to address the root cause". Only "plan ratified, implementation absent" leaves the spec untouched, and it is offered for the stale implementer session alone.
- **A decision the spec cannot hold** has a branch only under "When classification is Escalated" ("Decision recorded in this task's spec", "Decision belongs elsewhere … point there and reset"). A failure whose root is an undecided product question that no agent escalated goes through the standard menu, where the rescue settles it by writing a constraint of its own choosing.
- **Step 5.5, "Propagate findings to open tasks".** Each matching open task is offered "+ <proposed clause>", so the addition spreads to the neighbours; the non-convergence branch's third option, "Fold recurring spec-traceable nits into the task spec", likewise proposes "the minimal clause addition".

The phase gives the skill a statement of the rescue's purpose, that the task reflects what the system needs, and removes what presets the form of the root, so that whatever the root is, including a correct task the architecture is not ready for, can be said.
