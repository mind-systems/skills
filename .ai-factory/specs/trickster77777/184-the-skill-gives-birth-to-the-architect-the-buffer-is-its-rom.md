# Phase 66 — the skill gives birth to the architect, the buffer is its ROM

Governing spec: `docs/paired-loop.md`

The user's ruling: the behaviour an architect must keep holding lives in its buffer, and the seed is how it gets into every new one. "Он его читает, правит и перечитывает регулярно. Это позволяет ему не забывать и при этом не стараться помнить какие то вещи. А скилл вызывается раз на старте и через 10 сообщений он уже забыл что там было в скиле сказано. Скилл — рождает архитектора, буфер — его пзу." A rule read once does not hold; a rule re-read does. On the hand, in his words: "для редактора это ещё важней, чем для архитектора, тк он пишет." `docs/paired-loop.md` § "Where the pair's behaviour lives" states it: the behaviour both halves must keep holding lives in the buffer and enters every new one through the seed; the drain has two destinations, a project ruling to its artifact and the pair's base behaviour to the seed; at every rehydration the head reads the seed's standing entries against its own and takes the seed's text; what the user said twice, or what failed twice, is a debt to drain. The doc settles what the decomposition would otherwise have had to decide: which entries drain and which stay, and how a changed seed entry reaches a living buffer.

**Where behaviour lives now.** `templates/buffer-seed.md` carries the buffer's headings and, under `## Method`, standing entries for the counts rule and for what a spec holds. The counts entry has the writing half only: a measurement is not written, and what produces it is. `docs/counts-go-stale.md` has the reading half as well, that a figure which does appear is read as an order of magnitude and never failed on, and the seed does not. More of the pair's base behaviour sits in no seed: a rule states the behaviour and stops, with no sentence for each case it excludes; a task is not retold in the code; and the orchestrator's commit takes the whole tree. The last has a ground in code: `_git_commit` in `orchestrator/main.py` runs `git add -A`, so whatever the pair leaves uncommitted in a repository while a queue runs there lands inside a task's commit, and no skill or doc of this repository says so.

**The seed is read once.** `agent-architect` § "Spawn once, message thereafter" seeds a new buffer "read once, copied whole, never reread for a buffer that is merely resumed", and the seed's own opening says the same; the doc has the head read the seed's standing entries again at every rehydration. A living buffer therefore keeps the entry it was founded with, and a rule kept in a buffer has beaten a loaded skill in practice: a habit the engine had since decided against survived in a buffer and was followed over it.

**The drain has one destination in the engine.** `architect-editor-engine` § "The architect's buffer" says "A ruling recorded in the buffer is a debt against the skill, not a record of one. It leaves the buffer when it reaches the artifact that should hold it", and its frontmatter description repeats that form. The doc has two destinations and the said-twice threshold, which neither the engine nor `agent-architect` carries. Both halves load the engine, so it is where the drain is read.

**What reaches the hand.** `editor.md` has the editor load the engine and hold the buffer whole from birth; it never loads `agent-architect`, and its description names the architect as the only caller. A rule about how an artifact is worded reaches whoever writes it through the buffer, which is why the standing entries carry writing rules as well as the head's own.

**The spec side of comments.** How a task is written so that it is not retold in the source is the behaviour of whoever writes the spec, and the user ruled it this phase's own: "таски тоже должны писаться правильно без требования пересказывать таск в коде. … Мы описываем поведение агентов, через скилы и буфер теперь. И 66 фаза — именно этим занимается." The wording is the hard part, in his words "как это можно описать хер его знает": the behaviour is obvious and resists being stated. The evidence shows where the retelling starts. Where a plan commissioned a comment, it mostly did so from the spec's argument, with no order from the spec; in a skeleton task the spec itself ordered a class doc to carry the contract, though the skeleton skill asks for red tests and never for prose. The comment standard is shown by the user's own examples and defined nowhere: a comment that says what a reader would get wrong from the code alone, where the reader meets it, in a line or three.

**Not this phase, by the user's ruling.** Questions to the user put in behaviour (the agent asks in time and rightly), a check before asserting, and a ban on copies of project text in the buffer (an agent writes one to remember and cleans it up later) are not standing entries.
