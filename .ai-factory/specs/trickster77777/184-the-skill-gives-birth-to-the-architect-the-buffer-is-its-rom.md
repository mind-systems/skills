# Phase 66 — the skill gives birth to the architect, the buffer is its ROM

Governing spec: `docs/paired-loop.md`

The user's ruling: the behaviour an architect must keep holding lives in its buffer, and the seed is how it gets into every new one. "Он его читает, правит и перечитывает регулярно. Это позволяет ему не забывать и при этом не стараться помнить какие то вещи. А скилл вызывается раз на старте и через 10 сообщений он уже забыл что там было в скиле сказано. Скилл — рождает архитектора, буфер — его пзу." A rule read once does not hold; a rule re-read does. `docs/paired-loop.md` does not yet state this: § "What the memory holds, and who holds it" says who writes the memory and who reads it, § "Where the memory lives" and § "How the memory begins, and how it survives" say where it sits and what a snapshot is, and none says where behaviour lives.

**Where behaviour lives now.** `templates/buffer-seed.md` opens by saying it is read once at founding and copied whole; it carries the buffer's headings and, under `## Method`, one standing entry. `architect-editor-engine` § "The architect's buffer" lists what the memory holds — "the working discipline, the rulings the user has made about how the pair works, the method learned from repeated failure, and the register of where the skills still lag the practice" — and then states the drain rule: "A ruling recorded in the buffer is a debt against the skill, not a record of one. It leaves the buffer when it reaches the artifact that should hold it." The ruling keeps base behaviour in the buffer, and the drain rule sends every ruling out to an artifact. `agent-architect` § "Your buffer is shared; you alone write it" says when an entry is written and in what form, and leaves the shape and the drain to the engine.

**What reaches the hand.** `editor.md` has the editor load the engine and hold the buffer whole from birth; it never loads `agent-architect`, and its description names the architect as the only caller. A rule about how an artifact is worded, placed in `agent-architect`, therefore never reaches whoever writes it. The hand receives a rule only through `editor.md`, the engine or the buffer, and none of the three says which kind of rule goes to which.

**The threshold.** The user's theory: a phrase said to an agent once is noise, and said twice it becomes a constant; the buffer is where the repetitions collect. Nothing in the doc, the engine, `agent-architect` or the seed moves an entry that has been said twice, or has failed twice, to any home. The only movement is the drain, which takes an entry out when it reaches an artifact and never carries one up when it recurs.

**What a buffer should not hold.** When a neighbouring repository's architect trimmed its buffer, the largest group was copies of the global instructions and of project docs, already drifting in wording from their originals, and one rule that contradicted a loaded skill. This head's own buffer held copies of the same kind. The engine's list says what a buffer holds and never what it does not; `agent-architect` asks only that an entry be "what will hold again". A rule kept in a buffer has beaten a loaded skill in practice: a habit the engine had since decided against survived in a buffer and was followed over it.

**Candidates that cleared the threshold and have no home.** Questions to the user, put in behaviour and one fork at a time. And the spec side of comments: how a task is written so that it is not retold in the source. The user ruled it this phase's own: "таски тоже должны писаться правильно без требования пересказывать таск в коде. … Мы описываем поведение агентов, через скилы и буфер теперь. И 66 фаза — именно этим занимается." It is the behaviour of whoever writes the spec. The wording is the hard part, in his words "как это можно описать хер его знает": the behaviour is obvious and resists being stated, so it stays open here, and an example pair may carry it where a sentence does not. The evidence already shows where the retelling starts. Where a plan commissioned a comment, it mostly did so from the spec's argument, with no order from the spec; in a skeleton task the spec itself ordered a class doc to carry the contract, though the skeleton skill asks for red tests and never for prose. The comment standard is shown by the user's own examples and defined nowhere: a comment that says what a reader would get wrong from the code alone, where the reader meets it, in a line or three. These habits belong with it: the contract of a skeleton lives in types, signatures and red tests, and a comment whose subject retires is deleted unless it states a fact the code cannot. A clean-up phase in another repository has still to run, and its result tells the spec side from the orchestrator's prompt side; it is evidence to come, never a gate on this candidate.

**Open, for the decomposition to settle; this note does not answer them.** First, the drain rule says a ruling leaves the buffer once it reaches its artifact, while the ruling keeps base behaviour in the buffer: which entries drain and which stay? Second, a seeded entry is copied at founding, so when the seed changes, living buffers keep the old copy, and a rule in a buffer has beaten a loaded skill in practice: how does a changed seed entry reach a living buffer?
