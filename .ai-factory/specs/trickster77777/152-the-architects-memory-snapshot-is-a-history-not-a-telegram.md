# Phase 58 — the architect's memory snapshot is a history, not a telegram

Governing spec: `docs/paired-loop.md`

`src/skills/agent-architect/SKILL.md` § "Spawn once, message thereafter" describes the memory snapshot as carrying "only the volatile residue — where the work stands, what the hand knows, what will slip first, and what must not be resolved by inference — because everything durable already lives outside the conversation; never an inventory of the session." Every clause is true, and a file obeying it to the letter can still be useless: the roadmap, the specs, and the buffer already survive a compact untouched, so restating their state adds nothing, while *why* one option was taken over another — which premise turned out false, what corrected it, in what words — lives only in the conversation the compact destroys. Local evidence of the failure mode, not the field report's: `.ai-factory/handoffs/26-memory-snapshot-after-the-prune.md` was written this session in strict obedience to the current wording — "What happened, in the order it happened" states the field-report-to-phases path and the prune's disposal counts as bare fact, with no turn carrying the reason it was taken over an alternative; a successor reading it inherits the decisions and would re-litigate every reason behind them.

The supersession rule stays, scoped. The skill's own sentence — "Each new snapshot supersedes the last by name — the numerically higher-numbered one is the current one — so a reader never follows a stale next action" — is correct and not to be removed; the missing scope is what `.ai-factory/handoffs/29-the-architects-snapshot-is-a-history-not-a-telegram.md` supplies: supersession covers the *next action*, never the record. An older snapshot remains the history of its own stretch; only its closing instruction goes stale once a newer one exists. Without that scoping sentence, the plain reading is that older snapshots are disposable, which makes a history impossible to keep.

The file is written by the architect's own hand and never delegated — the current text forbids only delegating the *digest* ("the digest is your own recovery note and is never sent to the editor"), never the file as a whole, and that gap is exactly what handoff 29 names as the mechanism of its own session's failure: the architect handed its own recovery note to a hand that has neither the conversation nor the reasons behind any decision in its own context, and got back exactly the thin, inventory-shaped file the user rejected.

Thickness is the buffer's own settled ruling, not a judgment call made at write time to look finished: "Думаю по дефолту он всегда должен быть толстым, но иногда я могу попросить тонкий. Или по смыслу — передать список ссылок для поднятия контекста, вполне валидный тонкий хэндофф." A thin snapshot is a legitimate *form* — a pointer list for raising context — never a failed thick one, and the axis crosses both genres below.

Two genres share one directory and one numbering: the architect's own snapshot, and the project handoff `command-handoff` writes through `note`. `src/commands/command-handoff.md` composes a grid-shaped or prose-shaped artifact via `note`'s Step 3, populated by mining the session — a different reader (whichever agent comes next, on any subject) and a different composer (delegated, since `note` mines what the calling agent itself supplies as hooks) than the architect's own snapshot. The same request phrasing currently reaches the wrong one: per handoff 29, when the user says "we continue after the compact, bring the buffer current, write a detailed handoff of what we did and what came of it," he means the snapshot, not a `command-handoff` run.

Read directly rather than taken on the handoff's word, the exemplar pair in `/Users/max/projects/tradeoxy/tradeoxy_core/.ai-factory/handoffs/`: `67-memory-snapshot-before-the-compact.md`, the architect's own prose snapshot, opens "The project handoff for this stretch is `66-phase-54-closed-the-case-purge-and-two-rescues.md` — it lists what landed and what is open. This file carries what dies with the conversation: the order things happened in, why each turn was taken, what was wrong on the way." Its body is organized causally — "The arc, in the order it happened, and why each turn was taken," "What will slip first," "What must not be resolved by inference" — each turn carrying its own reason, e.g. "`54.7` and the 500 ms... The Transport bullet we had written the day before said 'the first snapshot is the connected signal' — a premise the broker's own code refutes." `66`, immediately before it in the same directory, is the project handoff for the identical stretch: grid-shaped via `note`'s template — Frame, Read-first map, Current state, Next step, Error log, Orientation, Domain model spine, Cross-cutting contracts, Per-unit map — organized by *what* changed and what to watch, not by why a choice was made over its alternative. The two read as complementary rather than redundant: `66`'s Error log records that four review premises were false; `67` explains, for one of them, the reasoning that overturned it. Genuinely two artifacts sharing an occasion, exactly as handoff 29 states, not a duplication.

The series read in order, filtered by which buffer each snapshot names, is the only record of how the pair actually moved — git shows what changed, specs show what was decided, nothing else shows why. `.ai-factory/handoffs/30-the-handoff-series-is-a-readable-history.md` measures this directly in the same project: nine handoffs cite `130-architect-buffer.md`, "exactly that architect's life, twelve days of it," navigable because each file names the buffer it belongs to.

The option of separating the two genres into different directories or filename prefixes was put to the user and declined, on migration cost against the files and pointers already written — not re-proposed here.
