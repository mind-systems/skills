# A recovered handle gets the new buffer's path, riding the next message

## Current state (grounded, read fresh)

`src/skills/agent-architect/SKILL.md` states two rules that were written apart and never reconciled against each other.

The first governs which buffer an architect works in at its own start: "Second, the buffer — and which of two starts this is decides what you do: a memory snapshot naming a buffer... means you work in that buffer, the same memory resumed, never a new one under an old name; no such pointer means you are a new architect and create your own buffer first, at the path and numbering the engine defines."

The second is the fallback that recovers an *editor's handle* when no snapshot reached the architect at all: "Where you hold no handle at recovery — never recorded, or recorded into a buffer whose path did not reach you (an auto-compact that fired before any handoff was written, or a handoff addressed elsewhere) — fall back to reading `~/.claude/projects/<project-key>/<session-id>/subagents/agent-<id>.meta.json`" — a file the same paragraph says lets the architect find "the editor's agent type, newest first by file mtime."

Nothing connects the two. An architect that reaches the fallback has, by definition, no buffer pointer of its own — the fallback's own precondition is "never recorded, or recorded into a buffer whose path did not reach you." By the first rule, that architect is "a new architect" and creates a fresh buffer. But the handle it just recovered from session metadata belongs to a live editor that was spawned by a *previous* architect run, already holds a path to *that* run's buffer, and — per the engine's own rule — re-reads that buffer's settled zone on change. The recovered architect creates buffer B; the recovered editor still holds and re-reads buffer A. Neither side's text says what happens next.

`src/skills/architect-editor-engine/SKILL.md` states the rule the recovered editor would need to act on: "The editor re-reads the settled zone when it changes, not once at birth." As written, that sentence covers the settled zone of the buffer the editor already holds changing in place; it does not say what the hand does when it is told a different buffer's path outright, which is exactly what the fallback-recovery case now requires. A send with no matching receive leaves the hand told and unchanged — the same two-live-memories failure this task exists to close, produced by the fix itself rather than by the fallback it repairs.

## The change

The gap closes with a rule, not a caveat: having recovered a handle through the metadata fallback with no buffer pointer of its own, the architect still follows the first rule as written — it is a new architect, and it creates its own buffer, at the path and numbering the engine defines, exactly as it would with no recovered handle at all. What the current text omits is the further step this specific path requires: the architect names its own buffer's path to the editor it just recovered, and that naming rides inside the next message it sends that editor as ordinary upkeep — the same mechanism `docs/paired-loop.md` § "What crosses the channel" now states for keeping a hand current: no form, no permission, riding inside whatever message is already going rather than travelling as one of its own.

State the reason this is the resolution and not either alternative the situation could otherwise fall into. Leaving both buffers live — the architect's new one and the editor's old one — is the silent-divergence failure the current text already produces and this task closes; it is not a resolution, it is the defect. Discarding the recovered editor and spawning a fresh one is available (the file's own respawn path already exists for a dead editor) but throws away a live, working hand with accumulated history for no reason tied to this situation — the editor is not dead, only pointed at the wrong memory, and the file elsewhere already treats losing a working editor as a cost, not a default ("Losing the editor is never fatal; losing it silently is the defect" — the same shape of cost this resolution avoids paying unnecessarily). Re-pointing the recovered editor to the architect's own new buffer is the only one of the three that keeps exactly one live memory and keeps the hand that was already working.

The engine's re-read rule widens to carry the receiving half of this same act: `architect-editor-engine`'s "The editor re-reads the settled zone when it changes" is read to cover not only its own buffer's content changing in place but also the editor being named a different buffer's path outright — either way the memory has moved, and either way the hand's obligation is the same: adopt what it is now told, replacing what it held, and hold one memory at a time. This is not a second rule beside the first; the existing sentence carries both cases once its own wording is widened to say so.

## Blast radius

This task edits the fallback-recovery paragraph in § "Spawn once, message thereafter," and only that paragraph in `agent-architect`. The respawn passage — the paragraph that opens "If the send fails, the editor is dead" — is 40.6's own territory, not a second site this task touches. This task also does not touch the memory-snapshot path (a snapshot naming a buffer already resolves which buffer the architect and its recovered editor share, since the snapshot is what let the architect find the buffer in the first place) and does not touch the liveness-probe mechanism ("attempting to send it to the recorded handle is the probe") — the probe still runs exactly as it does today, before this task's naming step has anything to ride on.

`docs/paired-loop.md` is not edited — the mechanism this task leans on (ordinary upkeep riding inside a message already going) is already stated there; restating it here would duplicate rather than ground.

`architect-editor-engine` is edited too, at its own re-read rule — widened, not restated: no new section, no new `loads:` edge, no restatement of the buffer's two zones or of the rule's own wording beyond what the widening requires. `editor.md` is untouched: the widened rule lives where both halves already load it unconditionally at birth, which is why it belongs there and not in the receiving side's own file — 40.3's reason for touching `editor.md` is its own, unrelated to this one.
