# Phase 73 — aif-architecture describes the built design first and asks where the system varies

The skill answers one question, how files are packaged, and has no step that asks where the system varies.

- **The menu.** `src/skills/aif-architecture/SKILL.md` § "Step 1: Recommend Architecture" offers, under "Architecture options", Structured Modules, Explicit Architecture, Microservices and Layered Architecture, and `references/architecture.md` § "Decision Matrix" picks among them by team size, domain complexity, scale and feature independence. Each answers where files lie and who imports whom. None asks where the system's variations live, modes, environments, providers, or where one is resolved. The reference's ports are interfaces to external systems (its principle "Port Abstraction for External Dependencies": databases, queues, third-party APIs), and its "Port and Adapter" example pairs a port with one adapter; a port with an adapter per mode is not described.
- **What it reads.** Step 0's "light codebase scan" reads package-manager files and the `src/` directory layout, and § "Step 1.5: Codebase Alignment Check" compares the chosen pattern's "ideal folder structure" with the real folders. Interfaces and their implementations are never read. Option 2 there, "Generate the pure, strict architecture guidelines (requires refactoring the application later to match)", writes a target, and `references/architecture-template.md` gives it the "Legacy vs New Code Policy" section; option 1 gives a "Code Organization Note". Neither describes the built design.
- **The field.** The user built the broker by hand as Ports and Adapters: `BrokerProtocol`, `ITimeProviding` and `IOrderBookSnapshotProviding`, each with an implementation per mode, chosen in a factory keyed by the subscription's mode, with `configure.swift` the composition root. The `ARCHITECTURE.md` the skill wrote for it, by the user's account and as the file's first commit reads, is titled "Architecture: Modular Monolith", calls its folder tree "the **target architecture** to migrate toward", and treats `BrokerProtocol` as a shared type under "Shared = protocols, not implementations", with no word of modes. In the core service the code slid into mode checks at every junction, and its file named only "Modular Monolith (NestJS Feature Modules)". Both files have since been rewritten by hand to name the port axis; they show what the skill should have produced, not what it did.

Three more observations, read fresh, that the decomposition cuts from:

- **This repository's own `.ai-factory/ARCHITECTURE.md` already holds the architecture the user wants, for skills, and is residue around it.** Its § "Composition: mechanism vs policy" is Ports and Adapters applied to skills: `roadmap-engine`'s maintenance flow is one logic flow whose caller-supplied hook points (a) granularity, (b) per-entry gate, (c) target-file routing and (d) extra update-mode actions are the ports, and `roadmap-outline` and `roadmap-decompose` are two adapters of it, each declaring `loads: roadmap-engine` and answering the hooks in its own "Hooks for `roadmap-engine`'s flow" section; `note`'s destination, template and verbosity hooks are the same shape. The section says it itself: "A philosophy skill invokes an engine for mechanism; the engine holds no policy and never drives." The rest of the file is the template's output. § "Dependency model" says "There is no import graph — invocations are runtime text instructions, not code dependencies", while every calling skill declares its edges in a `loads:` frontmatter field, which the repository's `CLAUDE.md` calls the forward graph. § "Skill categories" is a table of two rows, `aif-*` and "(none)" for "Domain skills (detangle, ui-ux-pro-max, …)", and names neither engines nor lenses, the kinds the file's own composition section establishes.
- **The orchestrator's `.ai-factory/ARCHITECTURE.md` is the skill's decision-matrix output, and its logic concludes that nothing varies.** Its § "Decision Rationale" reads "Team size: 1 developer → Layered" and "Domain complexity: low (coordination of calls, no business rules) → Layered", and the session that held that file argued from it, by the report, that the orchestrator needs no interfaces or invariants. The code holds real variation axes and rules, each read in `orchestrator/orchestrator/`: `main.py` defines `Mode` as a record of per-pipeline divergences (`verify_step`, `verify_fail_tag`, `output_suffix`, `pass_signal`, the planner prompt name) instantiated as `IMPLEMENT_MODE` and `TEST_MODE`, and beside that record `process_task` still branches on `mode.verify_step == "test_run"` to build a `TestRunner` and on `mode.verify_step == "review"` to find the previous review; the default roadmap pair keeps flat artifact directories while a named roadmap is keyed by its file stem (`_artifact_subdir` returns `None` for `ROADMAP.md` and `ROADMAP_TESTS.md`, and `process_task` branches on `mode.artifact_subdir`); the three LLM roles in `agents.py` share one runner, `_run_claude`, and differ in prompt, in declared tool list and in session policy (`PlanReviewer` is documented as a "Fresh session — no planner bias", `PlannerReviewer` and `Implementer` resume a session id), while `TestRunner`, which runs the plan's test command with no LLM, is the second implementation of the verify step beside the code review, not a fourth agent, with `_verify` in `process_task` its one call site, chosen by a string compare; `resume.py` `_detect_step` is a state machine over "plan", "plan_review", "implement", the mode's verify step, "done" and "escalated"; and `PLAN_REVIEW_PASS`, `REVIEW_PASS` and `ESCALATION` are a signal protocol read from the end of an artifact. The matrix measures size and reads simplicity from it; few lines is not few invariants. These invariants already have governing homes in `orchestrator/docs/`: the step values in `features/resume.md` § "`step` values", the file protocol and the signals in `pipeline.md` § "The file protocol" and § "Completion signals", the outcome invariants in `concepts/outcomes.md` § "Invariants"; the architecture file's Key Principles restate two of them, where links would serve. And the family's own lens never fired on any axis: `polymorphism-philosophy` fires when a kind gains its second member, and the mode, the verify step and the layout each have two, but nothing in that file names the kinds, so the question had nothing to be asked of.
- **The rule is one rule at several scales, and the skill sees it at one.** Hexagonal architecture draws the boundary at the system's edge; VIPER draws it again inside each screen module, with the Interactor as the use case, the Entity as the domain, the Presenter and View as the UI adapter and the Router as the navigation adapter, modules nesting; MVVM draws it inside the presentation layer. It is dependency inversion throughout: details depend on abstractions the core owns, which is Clean Architecture's dependency rule. The user builds this way and names it so: "все эти умные слова — тоже инварианты гексагональной архитектуры". `references/architecture.md` states the rule once, for the Explicit Architecture's whole-application layers ("Dependencies point INWARD. Outer layers implement interfaces (ports) defined by inner layers."), disclaims it for Structured Modules ("does not enforce … rigid hexagonal ports"), and names no pattern for the inside of a presentation layer. What the skill needs to see is where variations live and which way dependencies point, at each scale; the folders follow from that.

No document governs this; a skill is its own documentation, and none is written.

What should be true, for the decomposition to cut from and not a design: for existing code the skill describes the built design first, which interfaces have several implementations, where and by what key one is chosen, and names it (Ports and Adapters, the mode axis, the composition root), with folders second; it names the axes, their ports and the composition root, and links invariants to the documents that govern them, never restating them; for a new project it asks the variation axes before it shows the folder menu; a migration target is written only on the user's explicit choice.
