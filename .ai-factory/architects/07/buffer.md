## Open deferrals

- **A quoted phrase is not a usable sweep anchor in this family, and the failure is silent.** Our prose wraps at a fixed column — `src/skills/agent-architect/SKILL.md` runs to 99 code points a line — so a "distinctive phrase" of several words routinely straddles a line break in the source. A plain single-line `grep` for it then matches **nothing at all** and reports clean. Met twice in one pin-gaps pass, in two different specs, and in one of them it hid a second live occurrence of the phrase inside the very file being edited. By our own discriminator this is Class C: a check that can no longer fail. The repair is mechanical — anchor on a substring short enough to survive the wrap, and re-run the command before writing its result — but the trap is in the material, not in anyone's care, so it will recur. *Trigger:* it is very likely sitting unnoticed in the blast-radius section of every spec no pass has re-run; worth a sweep of its own when someone has the appetite.

- **Nobody in the pipeline runs anything, so "the review checks it" covers only what reading shows.** Read in the orchestrator's prompts: the reviewer reads the plan, `git diff HEAD` and the changed files, and executes nothing. The implementer runs the build and a vague "verify functionality works". So a property that only a run can show — say, that the in-memory tests pass without a database — is seen by no one unless the task asks for proof of it. The no-checks rule came out of this repository, where every property shows in the diff. `docs/what-a-task-carries.md` does not draw this line. The candidate line: a spec may demand proof of a runtime-only property, and must not write out the procedure for getting it. ## Working discipline

Keep the chat on substance. Investigation legwork goes to the editor as one `REPORT-ONLY` batch rather than a run of greps in the chat; file writes, scripts included, go as `APPLY-EDIT`. Verification of what landed stays with the architect — that is the layer that caught every discrepancy, including a silent bug in the architect's own analysis script. **The architect** never pastes its raw output into the chat: it states the conclusion in a line. The editor's own reports are the opposite — they carry the raw output to the architect, which is how a wrong expectation is caught, and `editor.md` requires it. A single decisive check is cheaper run directly than relayed.

**The marker and delegation are different axes.** `::` governs whose message crosses the channel: it forwards the *user's* payload for an independent read, and an unmarked user message is never forwarded. Delegating the architect's *own* legwork needs no marker and no permission. When the user's payload is relayed, the editor's agreement is signal and gets reconciled; when the architect's legwork is relayed, there is no second opinion in it — it is a hand, and treating its agreement as corroboration mistakes an echo for evidence.

**The architect writes handoffs, the buffer and rescue reports itself — because it holds the context, not because a rule forbids the hand.** A handoff is the architect's own context, and having something that does not hold it retell it produces an unpredictable result; the same goes for anything the architect authors from its own reading. This is a practice, not a boundary to enforce: the user has ruled that outside the buffer it does not matter whose hand wrote a thing, and a task naming the class was withdrawn on exactly that ground. Everything else goes to the editor by default.

**The pairing is a brush and its fingers, not a specification and its auditor.** The architect supplies meaning, constraint and place; the editor writes the artifact. Pin what a sentence must say and where it goes — not its characters — because a writer with the file open never restates what already stands beside it, and an architect composing replacement text blind does exactly that. What stays is mechanism, not ceremony: anchor by a unique string rather than a position, so two sessions editing one file do not collide; and read the landed result — not to audit the editor, which over a full session never once silently deviated, but to see what the decision looks like once it is real. Every defect that reading caught was the architect's own.

**Fingers explore a surface before anything is written about it, and whoever touched it writes.** A grounded section — what is true now, read from the code with exact values — belongs to the hand that had the file open, not to an architect who compressed a sweep into a claim and passed the claim on. The claim is where the detail dies: a grep showing six hits became "the shape occurs twice" in a spec when the file holds it once, because the output was read and the lines were not. The architect keeps the decision — what must change and why.

The split that governs it: a **factual** question (what does this line say, how many times does this word occur) is best answered by one careful reader who touches and writes, since two summarisers are worse than one; a question of **judgment** (is this task right, does it contradict a doc) needs two independent readings reconciled, and there the independence is the whole point.

**A delegated round is reconcilable when a second reading exists, not when the user's marker put it there.** The rule as written keys on who asked, and the pair has run many rounds against it, among them rounds where the hand read independently while the head walked the same ground and withheld its own read. Those returns were not echoes — twice the hand overturned the head outright, and more often it was sharper on a point the head had reached flatly. What a reconcile needs is two readings **produced independently**: existence and independence, both. Origin correlates and does not decide. Contamination is not the binding constraint either: the hand never held the head's in-flight read in the first place — it lived in the conversation, not in this file, which is why the zone erected to guard it prevented nothing and has now been removed. *Phase 48, which carried the skill-side repair, was deleted on 2026-10-02; this stays as method.*

**A ruling recorded here is a debt against the skill, not a record of one.** It is erased when it reaches the artifact that should hold it. A buffer that works well as shared context makes it more comfortable to leave rulings in it, so the drain tightens rather than relaxes.

## The discriminator that decides a check

`test-philosophy`, applied one tier up. **Silent failure → check it. Loud failure → do not.** A check that can only fail where the instruction was ignored describes a loud failure: the diff shows it on sight. Dropping a clause from a rationale is silent; not writing a pinned command is loud. A check that cannot fail on this repository at all — that an interpreter counts characters, that a file contains what was just written into it — is not a weak check but not a check.

## Standing method rule

Refreshed from `src/skills/agent-architect/templates/buffer-seed.md` at every rehydration; the seed's text wins.

**Standing entry — the counts rule.** It governs what is read later by someone who cannot ask back — a spec, a plan, a roadmap line, this buffer after a compact; in conversation a number or a position is fine, since a wrong one costs one reply. A number someone decided is written: it stays true however the tree grows. A measurement of the current tree is not written, dated or not — write what produces it, the rule or the search that gives it fresh each time. A spec least of all carries a number measuring the tree: tasks run one after another, and each one changes the tree the next was written against, so such a number in a queued spec is false before the orchestrator reaches it, and the orchestrator cannot execute a spec whose facts no longer hold. A number met in a spec, a plan or a report is read as an order of magnitude; one that has gone stale is not a defect to correct, count again or stop on. Two counts that disagree are not reconciled against each other; ask which member is missing.

**Standing entry — what a spec holds.** A spec states what is true now, what must be true after and what breaks on contact, and nothing else. It carries no check that the instruction was carried out: the orchestrator plans, builds and reviews on its own, and a check written into a spec comes back as plan steps and review rounds. It names no position in a file, only what the artifact must hold. It puts no fence around a neighbour; scope is what the task changes.

**Standing entry — state the behaviour and stop.** A rule says what happens and ends there: no sentence for each case it excludes, no guard against its own misuse. A rule or a fix that needs guards against its own machinery is the wrong one.

**Standing entry — a task is not retold in the code.** A spec's reasons are for whoever plans, and the code keeps none of them. A task says what must be true and what to delete or link; it never asks for a comment carrying its reasoning, a skeleton's contract or its scope. A comment in code says only what a reader would get wrong from the code alone, where the reader meets it, in a line or three.

**Standing entry — the orchestrator's commit takes the whole tree.** While it runs a queue in a repository, leave nothing uncommitted there, or it lands inside a task's commit.

The governing account of counts is `docs/counts-go-stale.md`. What stays, because the doc does not carry it: `§ N` addresses by position, which is a defect of the same family as `file:line` but about space, not quantity — phase 42 carries it, and `docs/reference-by-name.md` governs it.

**An always-loaded prohibition loses to a loaded procedure's instruction at the moment of writing, and this is not a habit to be disciplined out.** The global CLAUDE.md forbids a position address in any durable artifact; `roadmap-outline-deep`'s verbosity directive asks for "a `file:line` where a claim needs one"; and every phase note in this folder carries them, the newest written minutes after the pair had discussed the prohibition out loud. The hand was not careless and does not need reminding — it executed the procedure it was running. This is `docs/instruction-in-data.md` read in the other direction: what lives in the step executes, and what lives only in the always-loaded layer does not beat it. The prediction is checkable rather than arguable: repair the directive and the instances stop appearing, with no appeal to vigilance anywhere. The directive is repaired (phase 65); do not treat a fresh instance as evidence of an undisciplined hand.

**In this repository the plan and the thing planned are the same material, so the boundary between them is invisible to the hand.** A decompose round drifted into applying its own target edit — the hand began rewriting `agent-architect`'s paragraph while writing the spec that describes rewriting it — caught it itself, reverted, and reported. Elsewhere the boundary is obvious: a spec is prose and the product is code. Here both are English in markdown, and nothing in the material announces which one is being written. So an order for a planning round says what it produces **and what it must not touch even though the spec describes touching it**, and a verification of a planning round checks that the target files are still clean, not only that the specs exist.

**A rule read wider than it governs manufactures work that looks like real work.** "Two channel-message formats, nothing else" governs what opens a round. Read as an account of everything the head may ever say, it generated three vehicle problems in one phase, each of which felt like a genuine finding, cost a round, and in one case removed a mechanism from the governing spec. The tell is that the difficulty is always about *permission to say something obvious*, never about the thing itself. When a task keeps stalling on where something is allowed to travel, suspect the rule's scope before designing the vehicle.

**A term belongs to the file that defines it, and a spec borrowing one inherits its meaning.** A spec about `editor.md` used that file's own phrase — "architect framing", defined there as *no pre-loaded findings, checklist or verdict* — to mean *the architect chose the topic*, two sentences from the definition. Read literally it licensed what the engine forbids, and it made the task larger than the defect. The registry's one-word-one-meaning rule does not reach a target file's local vocabulary, and this is the same failure without it: before reusing a word the target already uses, read what the target means by it, or say the thing in your own words.

The other direction is the one that catches you unawares: **a phase's own shorthand leaks toward the artifact.** Working through a phase you invent a compact name for the thing under discussion — it earns its place in the chat and in the orders, and then a spec writes it down as though the target file knew it. The target had a construction of its own and never needed a noun. The tell is that the term reads fluently to everyone who sat through the phase and appears nowhere in the file being changed.

**A removal has a blast radius and nothing computes it.** Everything named below is one shape: what leaned on the removed part is not reported when the part goes. Three instances in one day. A clause replaced in a contract line orphaned two references at once, because the clause held the only naming of what both reached for. A task narrowed dropped a repair its wider version owned — the reason for that repair had not gone away, only the half of the task that happened to carry it — and left a sibling spec pointing at reasoning that no longer existed. And an unread deferral says the same thing one tier up: a sentence is not a unit of claim. An addition does it too, in the other direction: naming a second thing where one was named breaks every reference that resolved by being the only candidate — a pronoun in the next sentence, a definite article three lines down. Neither end is caught by reading the change; both are caught only by reading the neighbourhood whole, after.

**A clean pass is a property of the questions asked, not of the task.** A walk over one task came back with nothing, and the defect was sitting in its landing text the whole time — the order had asked about scope and about geography and never about vocabulary. Reporting "nothing found" as though it described the task is the error; what it describes is the order. When a pass returns clean, the useful next thought is which question would have found something, not that there was nothing to find.

**A rule's home is decided by when it must be readable, never by what it is about.** 36.3 put "no architect reads another's buffer" into the skill that governs two architects working together — matching the rule to its subject. That skill loads only where the user has assigned a pairing role, and the rule holds wherever a second architect exists at all, pairing or none; this repository is in that state now, with three buffers on disk and no role declared. The rule would have been absent exactly where it applies. Before choosing a home, ask what must be resident at the moment the rule has to be obeyed — subject matter is the wrong axis and reads as the right one.

**A rescue's own repair is a specification change, and it can plant the next failure.** The first rescue of 36.1 corrected a rule that sorted buffer entries by category, replacing it with a test that sorts by what an entry is. The correction was right about the sorting and said nothing about where the rule would live — so the specification decided a test, granted the engine two characterisations, forbade the architect to restate anything, and left the pointer aiming at a rule no change list writes. The next run died on exactly that, twice over, and the second rescue removed the test the first one added. Repairing under the pressure of a failed run is when a new claim is least likely to be housed: before adding one, name the file that will hold it.

**Lifting a constraint means stating what it was protecting.** "Do not trim to stay under the ceiling" removed a number and left no criterion, and the line came back at 1511 code points doing the spec's job — obeyed exactly, and wrong. The number was never the point; the two-tier split was. The same shape appears in a guardrail drawn around a section instead of around a claim: a boundary named without its purpose is followed to somewhere neither of us wanted. Name the purpose and the hand steers by it; name only the edge and it optimizes for whatever is left.

**An edit to a governing spec reaches that phase's note in the same round.** The note states what diverges *now*, measured against the doc; move the doc and the note's measurements are taken from a line that no longer exists. The failure is not staleness but inversion — a note that said something was undocumented on both sides reports the opposite once one side documents it. Two skills read the note in full and unconditionally: decomposition before a phase's first task, and rescue when judging a failure against its second baseline. A rescue reading an inverted note diagnoses against a false baseline and prescribes the wrong repair, which is the most expensive mistake in the cycle. When scoping a round that touches a doc, the phase note is inside the boundary, never outside it.
