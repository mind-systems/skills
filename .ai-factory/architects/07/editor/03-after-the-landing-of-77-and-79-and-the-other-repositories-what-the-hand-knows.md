## The material, and where it bites

**Other repositories through git objects.** The orders say: remote refs only, `git show <ref>:<path>`, never a checkout, working trees left on their branch. Sub-repositories sit on a feature branch and the interesting code is on a remote ref, so the working tree is stale for the question. Read `git log <ref>` and `git ls-tree -r --name-only <ref>` first. Product agents' prompts and the gateway's configuration live in volumes outside git; say so plainly instead of quoting what is not there, and mark every inference. Dates in a code comment are evidence of when something happened; a commit's author date and its landing date differ. On this machine's shell, `$R:tg-client` is read as a path modifier and silently breaks the ref: write `${R}:path`. An unmatched glob aborts the whole command line, so quote `--include` patterns and expect `no matches found` when a `ls` or `grep` has none. The BSD `head` refuses a zero count. A helper script written to `/tmp` is removed before the report.

**Gate scanning.** An entry is a column-0 `- ` line under the heading; indented lines below are continuation, and the marker goes at the end of the column-0 line. A scan that looks for the marker at the end of the line is the right check, and a scan that finds nothing unpinned has to be re-run after the writes.

**Writing a phase.** The numbering of specs is by the highest number in the folder, and a number the coordinator names can still be free while a pruned number is not; check the folder. A preamble's budget includes the pointer, and the pointer is long: compute the pointer's length first and cut the prose to the remainder, not the other way. Each phase in the file sits under its own direction header. The `Governing spec:` line comes first, above the preamble. Contract lines run to the range the engine names; measure, do not estimate. A task's place in the file is its order, and no line says anything about order.

**Docs.** Docs wrap near ninety columns and a rewrap needs a re-read after. The futures folder holds documents marked as undetermined possible futures, and each new one gets a row in the project `CLAUDE.md`; a row of an existing doc is extended by a clause when the doc grows a thread. Our docs name no side project; the sakshi family now includes the herald, so the herald can be named in the root, but the friend's project read through git stays out of docs and notes.

**A sweep is a command and a result.** Every spec carries a sweep and a finding, and the finding is a statement about the command's output on the tree as it is. Run the command before writing the finding.

## Where I was wrong, and the pattern

A finding written from intent. In the first draft of the field-doc spec I wrote that the `CLAUDE.md` rows were among the texts the sweep reaches; the sweep never returned them. The coordinator caught it when told to run each sweep fresh. The pattern: I knew what I meant the sweep to find and wrote that. Run, then write what came back.

A sweep pattern that straddles a wrap. Found in specs already written by others; the cure is a short substring that fits one line, or a second anchor next to it. A sweep whose only anchor wraps reports clean and is wrong.

A criterion that was a list in disguise. The first reason I pinned for which skills stay out of the field was "invocation acts", and the planning lenses act too. What sets the flagged ones apart is that their work is reviewed only before it happens. The flaw came with the order, and I should have asked of the criterion what it excluded: test a reason against the case it is meant to separate before writing it into a doc.

A phrase copied from the neighbours. "Sequenced after" appeared in an earlier contract line of this file and I carried it into a new one, and it came back after being removed. Copying the shape of neighbouring lines copies their habits; the form comes from the engine's rules, not from the line above.

A clause in the wrong place. A contract line's change clause must say only what the pinned text says; the reason for it goes before the clause. A lens remark placed inside the clause would have been written into the doc by a planner and rejected by the reviewer.

Counting words again. "Four", "both", "two" got into notes and specs as tallies of named members. Name the members; leave the number out. The search for number words over my own text, before reporting, is the habit that catches it.

A claim from an early read. I said the earlier snapshots had no writer line, from memory of the first read, when they had since gained it. When a file may have moved, read it before describing it.

An inherited premise. An order said the source field in other projects never names a document or a ruling; the files showed that some values do. Checking the premise and writing what the files support was right, and it is the habit to keep. The Claude Code documentation quotes in note `0221` were inherited from an earlier note and not re-verified here; if an order depends on them, they cannot be checked from the files.

## What will slip first for a hand without my history

Running before finding: a sweep's finding comes from its output on the tree as it stands.

The anchor: a sweep pattern is short enough to sit on one line in every file the finding names.
