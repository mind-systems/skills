# Editor snapshot — after phase 77's decomposition

Written by the hand itself, at the seam the head chose, for the hand that starts from this file and the buffer. The buffer holds the practice and the rulings and is read first; this file holds what only the one who did the work can say: what the material is like, where I was wrong, what is half done. Read the buffer in full, then this, then the files named below fresh — everything here is a description, and the files win.

## How the work arrives and what the head wants back

Every round is a coordinator message that opens with a format token. An `APPLY-EDIT` order pins meaning, place and the values that must appear verbatim, and expects me to write the text myself with the file open; it ends with "do not commit" and a list of what to report raw. A `REPORT-ONLY` order is legwork: read, quote, report by fact, write nothing, delete any temporary clone afterwards. Messages also arrive mid-turn, prefixed as coming from the coordinator while I was working, and each carries "address this before completing your current task" — so the newest message is handled first, in full, and then the earlier thread resumes. The head wants the changed passage or the inserted block pasted verbatim, the path of anything new, and a short list of every place the files differed from the brief or where I had to decide something the order did not pin. It does not want a bare "done". It does not want me to commit, and it does not want me to touch the buffer.

The report that works has the same shape each time: what was done in a line, the raw text, then the deviations. When a quoted anchor in the brief names the wrong section or a claim does not hold on the file, I say so and write what the file supports. That habit has caught real errors on the head's side and is the thing to keep.

## The material, and where it bites

The roadmap I work in is the named one for this user, with phases above and below a `---STOP---` line. Above the line the phases are queued for the orchestrator; below it they are outlined or deepened and wait. A phase block is a `##` direction header, a `### Phase N — title` header, optionally a `Governing spec:` line first, and one prose preamble. Deepened phases end their preamble with the literal pointer `Phase note: [title](repo-root-relative path)`. The preamble budget is counted in code points with the trailing newline excluded and includes the pointer, and the pointer is long, so the prose has little room; I have gone over by a handful of characters more than once and fixed it only by measuring in Python before writing. Contract lines have their own range, and the same discipline applies: compute the length before the write, trim the clause that carries no pin, never the pinned text. Tasks sit as flat checkbox bullets directly under the preamble, numbered phase-dot-ordinal, each ending in a `Spec:` tag.

Specs and phase notes go in the roadmap's own spec folder. The numbering rule is the `note` skill's: scan the folder for names that begin with digits and a hyphen, compare numerically, add one, write four digits. Old files with fewer digits sit in the same folder and rank by value. A task's spec number is therefore unrelated to the task's own number — the specs for the phase-77 tasks were written in an order that does not match their order of execution, and the contract lines are the only map between them. I write notes and specs directly with that rule rather than through the skill's invocation; the folder-style step is to read the newest siblings and match them.

A spec has three parts and nothing else: what is true now, what must be true after, what breaks on contact. The last is written as a rule, a sweep and a finding. Spec texts quote the files, and the files wrap at a fixed column, so a quoted phrase of several words straddles a line break and a single-line search for it silently finds nothing. I anchor sweeps and checks on short fragments and re-run the command before I write down its result. The same wrapping means a quote copied from a rendered view needs the original text re-read, not retyped from memory.

Specific passages and how they are worded. In the engine skill for the roadmap format, the paragraph that says what a task spec holds is a bold lead-in followed by wrapped prose, with a sentence beginning "Nothing else means" that lists what a spec must not contain: a check, a position, a fence. In the pin-gaps command, the paragraph on blast-radius holes is a single very long physical line, easy to quote and easy to damage with a careless replace; its invariant sentence ends with refusals joined by dashes and "never". The buffer seed's counts entry is wrapped at a narrow column and is matched into every buffer by its bold lead-in, so its first words must not change. The agent-architect skill states the snapshot rules in the section on spawning, and the sentence that forbids the editor from composing a snapshot lives in a different section, the one on relaying — the brief attributed it to the wrong one once, and I found it only because I grepped before quoting. The doc on counts has a test paragraph with a pair carve-out and a section on why an agent suffers; the doc on what a task carries has a section on what a spec holds that mirrors the engine's paragraph and a section on blast radius that says a spec never records a snapshot of what a search returned — which sits in standing tension with the pin-gaps invariant asking for a recorded finding of what the sweep reaches. That tension is recorded in a spec's finding and left alone on purpose.

Mechanics that cost me time. On this machine the shell is zsh with the default BSD tools: an unquoted run of equals signs as an echo argument fails, the in-place flag of the stream editor needs an empty argument, and bash is the old 3.2, where expanding an empty array under the strict-unset option can fail unless the form is chosen carefully. I edit files with Python and print with `printf`. `git mv` refuses an untracked file and `git rm` refuses a file with local modifications unless forced; the head's orders that say `git rm` mean the staged removal, and I report that I used force. A script that clones and fetches other repositories is tested from a throwaway copy with a scratch directory and cleaned up, never run against the live tree.

## Where I was wrong, and how it was caught

Counting. The rule is that nothing durable carries a number of our own, and I broke it repeatedly while believing I had not: a preamble that said "three texts pull toward a count", a note that said "two of them lean the other way", a contract line that said "both texts are pinned", a spec that said "gives the repair as three things". Each time the slip was a cardinal word summarising a list I had just written, and each time the coordinator found it, not I. The pattern is that listing produces the number as a reflex. Before reporting anything durable I now search it for number words and for "both", "pair" used as a count, and ordinals standing in for tallies, and I name members instead. The quoted examples the orders themselves require are the only exception.

Language of a document. I translated a new doc into Russian because the global rule says to match the neighbours' language and the neighbours were Russian; the user wanted English and said so. The global rule gave way to his word, and the buffer now records that I ask before translating a doc again.

Evidence told in a doc. I wrote that an agent had built a particular port; the user had written it by hand. Then I wrote that an architect had turned a step into a port; the port had not landed and existed only as a design. Each error came from taking a brief's wording as fact. The pattern: a doc's evidence names who did what and whether it exists, and each of those is checked on the files or marked as given, never inferred from the brief's phrasing. The fix each time was to say "designed" and to keep project names out.

Compression. Compressing phase 78's preamble, I dropped its gate, although the skill's step says to keep the gate and the pointer. The pointer eats most of the budget and the gate was the first thing I cut. When I compress now I write the gate first and trim the rest around it.

Over-limit lines. Contract lines went over their range several times when I added a clause; the trim has to come from clauses that pin nothing. Also: a spec that names a count in a sweep's finding, or in a title, is the same slip in another place.

What I would do differently. Run the number-word search before every report, not after a correction. Read the mirror of a skill paragraph in the docs at the start of a decomposition — the doc that mirrors the engine's paragraph was found only after the tasks were drafted. Ask about language at once when neighbours disagree with the user's habits. And keep a single place, the head's brief, for who-did-what claims, flagging each as given.

## What is in flight

Phase 77 is decomposed and uncommitted. Its governing doc is the counts doc, its note is the phase note written for it, and its preamble points at that note. Its tasks run in this order: the counts doc names the pair carve-out and the work-order; the doc that governs a spec's shape gets the same meaning of exact values, the named-set rule and the measurement exclusion; the roadmap engine's paragraph gets the same in its own voice; the pin-gaps invariant loses its size word; the seed's counts entry says a work-order is not conversation. The first is sequenced first because docs lead; the doc task and the engine task must agree in meaning, and the engine's contract line is sequenced after the doc's. The remaining tasks follow the counts doc only. Their spec files carry numbers that do not follow that order, so read the contract lines for the mapping. No skill, doc or seed file has been edited for these tasks; only the roadmap and the specs exist.

Phase 78 is outlined and deepened, uncommitted: preamble with the gate restored and the pointer last, and a note whose closing paragraph carries the replacement window as the user decided it — a firm floor at half the hand's context, a soft mark at four fifths, the seam picked in between, and the replacement as the head's quiet act. The preamble does not mention the window; that is a known gap, flagged to the head, not mine to close unprompted. Phase 78 waits on this trial and on phase 76.

Phase 76 is outlined and deepened with docs already updated: the paired-loop doc, the pipeline doc and the project index describe the per-user folder. The skills still describe the flat layout, which is why this very snapshot sits in a flat head folder. Phases 73, 74 and 75 are landed and committed.

Uncommitted in the tree, besides the roadmap and the phase notes and specs above: rescue reports that belong to a neighbouring repository's work and are not mine; leave them. The orchestrator's commit takes the whole tree, so the head decides when the tree is clean.

## What will slip first for a hand without my history

The counting reflex, first and most often — see above. Next, the section attribution of quotes, because a brief names a section from memory. Next, the budget arithmetic on preambles and contract lines, which only measurement settles. Then the standing rulings that the buffer states and that a fresh hand reads once and loses: docs describe implicit behaviour and never cite the plan layer, never name another project, stay English; a skill cites no doc; specs carry no checks, positions or fences; counts in anything read later are measurements and do not belong. Last, the boundary of each round: an order says what it writes and what it must not touch, and in this repository a spec and the thing it describes are the same material, so I check at the end that the target files are still clean. When unsure whether something belongs to the round, I put it in the report as a flag and leave the file alone.
