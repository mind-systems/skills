# 93.15 — Negatives no one pinned

**Project:** tradeoxy_core
**Date:** 2026-10-16
**Stopped at:** planned:3
**Elapsed before the rescue:** 703
**Sessions:** planner: 63253a95-fa90-46a2-9c8d-0386a5c2bb88; plan-reviewer-1: 0c48c9a3-189b-4b95-af9f-8294398edf99; plan-reviewer-2: 87b04d93-b82f-4de3-9643-ba4424e82310; plan-reviewer-3: 99025662-1539-4836-98d1-e1df84ad38e0

The task stopped in planning; no code was written and nothing escalated. The governing doc, what a bar is, was not violated by any plan. Its catch-up paragraph says a catch-up that has not landed by the bar's boundary does not hold the bar, which goes out at its boundary with what core has, and that is what every plan built. The phase note records no divergence that matches the findings, and it is silent on the one design question the last review parked. The failure was in the task spec, not in the ratified contract.

The task let the bucket detector take in past data: a set of past sources added to the buckets that are forming, a way to hold a bucket incomplete while a gap's trades are missing and fold those trades in later, and a query for how far back a catch-up must read. The spec stated the rules of each operation correctly and listed its test cases by name only, with no instants, no sources and no expected outcomes. Every concrete case therefore had to be invented by the planner, and each invented case was written loosely enough to pass against a wrong implementation or to be unrunnable as written.

The first plan had three faults, all in its tests. The test for the one-week series computed its expected value with an expression that does not compile, because the grid lookup returns a type that has no start method; only the clock-grid type has one. The case "a source for another bucket is ignored and no bucket is created" was false for a pair, since the wider fixed series (five minutes up to an hour) hold both the instant and the source and rightly take it; the spec's own sentence about priming is per series and correct, but its test line was stated for the pair, and the plan copied the line. The lost-gap case described a state that cannot occur: a five-second bucket that becomes whole is sent out at that very second, so a mark can only land while the bucket is still forming, and the plan's steps could not produce a warning at all. The spec fixes none of this, although it names the task that makes a whole bucket leave at once.

The planner fixed all three, and the second plan stumbled on a different omission of the same kind. The rule that priming emits nothing was written in the spec's prose but named no sources in the plan's case, so an implementation that emitted a bucket it had just completed would pass silently, with an early closed bar and no error. The case for a trade whose bucket is already gone asserted only that nothing throws, so an implementation that re-created the bucket for the trade would pass and later send a spurious partial bar.

The planner fixed those as well, and the third plan again left one rule unpinned: a series that holds a bucket with another open is left alone. The case named no source. The natural choice, a source next to the held bucket, falls outside the bucket that holds the priming instant, so the series is skipped before the branch under test runs, and the case passes whatever that branch does. A likely wrong implementation, copying the left-behind handling of the live path into priming, would have emitted the old bucket partial and replaced it without any test noticing. The same review parked an observation outside its findings: because a series that has just sent a bucket out and a series that never started both hold no bucket, priming would build the sent-out bucket again whenever a catch-up lands on core's clock with an instant inside a bucket the stream, which closes seconds on exchange time, has already closed; the next live second would then send it out a second time, partial, with a warning. That is a question the spec itself leaves open, and it conflicts with the catch-up contract's promise that a result landing after its bar's boundary changes nothing.

Each repair held, and each review found the next unpinned negative. Of the six test findings across the reviews, four are the same defect, a negative assertion that goes vacuous instead of red, and the spec's section on what breaks on contact held one search and enumerated none of its negatives: nothing is emitted, a bucket with another open is untouched, a gone bucket is not re-created, a bucket outside a gap is not marked. At that rate every review would find one more, and the reviews' remaining candidates were visible already: buckets outside the marked interval stay unmarked, a key clears only itself at detector level, the two operations create no bucket and no container for a pair that has none, and the plan's first case still offered a choice between two source sets.

The task also carried two behaviours under one line: adding past sources to the buckets by cover, with the query for how far back to read, and holding a bucket incomplete with folding trades in without moving the cover. They share no state or invariant, serve different callers in the catch-up that follows, and change `TimeBucket` by two disjoint mechanisms. The open design question lived only in the first. A file that must be described with an "and" carried the findings of both halves.

Classification: specification gap with a scope-overload signal; the same kind of finding recurred in all three reviews.

> The spec must pin each of its negative outcomes, that priming emits nothing, that a bucket with another open is untouched, that a gone bucket is not re-created, that a bucket outside a gap is not marked, with the source and the instant that make it observable, and must say whether priming may create a bucket for a series whose bucket was already sent out; had it done so, no review would have found a vacuous case and the re-creation question would have been decided before planning.

## What was done

The task was split by the roadmap's sub-numbering rule. The first part, 93.15.1, holds the gap's mark and its trades: marking and amending on the detector, and folding without cover plus the lost-set on `TimeBucket`, with `isWhole()` false while a key is marked. It has a new spec, `.ai-factory/specs/0368-the-gaps-mark-and-its-trades.md`. The second part, 93.15.2, keeps the original line renumbered and the spec `0364`, rewritten in place: priming, `PrimeSource` and the earliest-bucket query, plus one new rule decided by the architect on the side of construction over timing. The detector remembers, per series, the open of the last bucket it emitted, and priming never creates a bucket at or before that open; the memory is cleared where a series' state already ends, in `dropPair`, `onEmpty` and `onModuleDestroy`. The spec states why: seconds close on exchange time while a catch-up lands on core's clock, so only the detector knows a bucket already went out, and a bar never goes out twice, which makes the catch-up contract's "a result landing after its bar's boundary changes nothing" hold by construction. The order is 93.15.1, then 93.15.2; the contract lines are 868 and 713 characters.

Both specs now pin every case with its instants, its sources with widths, its series and its expected outcome, negatives included, covering the fixes of all three reviews and the four candidates the diagnosis predicted. Wider series that rightly take a source are named as such, never as "no bucket"; the one-week case narrows the grid with the clock-grid guard; the mark case sets live seconds up before marking; and the refusal to re-create a sent-out bucket has its own case. The catch-up contract's state sentence now points the mark and amend at the new spec and keeps priming and the earliest-bucket query at the old one, and the catch-up run spec points its gap bullet at the new spec.

The attempt's plan, its three plan reviews and its sidecar were deleted after this report was written. The deferred observation in the last review was not pinned: it was routed into the rewritten spec, and the review file that carried it no longer exists.
