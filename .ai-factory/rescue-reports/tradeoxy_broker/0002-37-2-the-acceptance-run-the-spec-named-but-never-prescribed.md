# 37.2 — the acceptance run the spec named but never prescribed

**Project:** tradeoxy_broker
**Date:** 2026-09-24
**Stopped at:** planned:3
**Elapsed before the rescue:** 1432 s

The task is small, and as a code change the plan was right from its first draft. It replaces both `fatalError` calls in `ensureTestDatabaseExists(named:on:)` with a throw of a two-case error enum carrying the old messages verbatim, confirms no signature needs to change, and sweeps every `try configure(app)` in the test target to make sure no enclosing `catch` swallows the new error. The first review confirmed every one of those claims against the code and found nothing critical, but it caught the closing measurement. The plan asked that a run without a database end with the database-backed classes red and `OrderProfitCalculatorTests` and `CumulativeProfitRecordTests` green. The reviewer pointed out that those two are examples, not the set: thirty-five test classes never boot a database, and thirty-three of them have never once executed without Postgres, because today's `fatalError` kills the process at whichever database-backed class runs first. The phase's own decision reads "leaves every in-memory test in the same binary running"; the measurement checked two. The same review also caught a false language claim offered as the reason for declaring the enum at file scope.

The plan was revised: the measurement now demanded every non-database class green and named that set by `grep -L`. The next review accepted both repairs and found two new gaps, again in the measurement. The step had no disposition for the very outcome it existed to detect — an in-memory class failing for its own pre-existing reason left the implementer choosing between editing test files it had been told to only read, and checking the box over a governing-doc sentence the run had just falsified. And the environment override was unpinned: "`DATABASE_HOST` pointed at a closed port" reads two ways, and they differ by about eleven minutes, since an unreachable address stalls postgres-nio's default ten-second `connectTimeout` at each of the sixty-five call sites, while a closed port on a resolving host refuses at once.

The plan was revised again, pinning `DATABASE_HOST=127.0.0.1 DATABASE_PORT=1 swift test` and adding three outcomes with three dispositions. The third review accepted all of it and found the last gap, once more in the measurement. The spec's own `## Tests` names two loud-failure discriminators: the process still dies, caught by the no-database run, or a database-backed test goes red for a reason unrelated to a missing database — "caught by ordinary `swift test`". The plan prescribed that ordinary run with a live database nowhere, and under `DATABASE_PORT=1` the second outcome cannot be seen at all, since every database-backed class is red anyway. The reviewer showed how this bites this exact diff: if the `42P04` branch stopped absorbing the benign "already exists" case, or the success-path `close()` were disturbed while the adjacent `catch` was rewritten, the no-database run would look exactly as predicted and the task would be marked done over a regression.

Every finding across the three reviews landed in one place: spec `0024`'s `## Verification`, a single sentence — "With `DATABASE_HOST` pointed at a closed port, `swift test` ends with the database-backed classes red, `OrderProfitCalculatorTests` and `CumulativeProfitRecordTests` green". It states two examples as if they were the set, leaves the override ambiguous, and describes only one of the two runs its own `## Tests` relies on. The first of those is a direct divergence from what was already ratified above the task: phase note `0013` § Decisions — "leaves every in-memory test in the same binary running" — and `docs/testing.md` § Behavior without a database — "In-memory tests run and pass." The task spec failed to carry what the phase had already decided.

> The spec's verification should have prescribed two runs — an ordinary `swift test` against a reachable Postgres with every class green, then `DATABASE_HOST=127.0.0.1 DATABASE_PORT=1 swift test` with exactly the database-backed classes red and every other class green — with an explicit disposition for an in-memory class that fails for its own reason.

**Classification:** specification gap; recurring signal — the `## Verification` of spec `0024`, a finding in every one of the three reviews.

## What was done

Repaired at spec + plan depth. Spec `0024`'s `## Verification` now states both runs in order, the ordinary one first so a pre-existing red is attributed before the override run, with the literal override and both reasons for it (immediate refusal versus the ten-second connect timeout; the process environment winning over the repository's `.env`), the database-backed and in-memory sets named by the `grep -l`/`grep -L` partition rather than by count or by example, and a disposition for each failure mode; its `## Tests` now points each discriminator at its run. The `37.2` contract line gained one clause stating the two-run acceptance. The plan, which had already closed five of the six findings, gained the ordinary run ahead of the override run and had the "red for an unrelated reason" disposition bound to it; nothing else in it changed. The three plan reviews were deleted; the plan and its sidecar were kept, with the sidecar reset to `planned:1` and the planner session preserved.

Two observations the deleted reviews carried were disposed of before deletion, since no other file held them. Phase note `0013` had described the classes reaching the bootstrap as a named count of six, and still recorded "a per-run suffix" as the decision for the shared test-database name — the decision task `37.3` settled the other way, with an advisory lock around migration. Both statements were corrected, along with the same superseded decision in Phase 37's roadmap preamble, so that `37.3`'s planner does not read the rejected design first. The second observation — three `StagingBrokerSimulateFill*Tests` comments claiming the global `log()` is a no-op when `App.shared` is nil, which it is not — was routed into a new `ROADMAP_TESTS.md` entry with its own spec `0048`, rather than dismissed, because the finding is true and its only record was about to be deleted.

The same class of gap was propagated to the next task in run order: spec `0025`'s verification now pins the test database's literal name, `tradeoxy_database_test`, and states that its runs need a reachable Postgres; and task `37.3`'s contract line had its advisory-lock statements corrected from a `$1` positional binding, which `PostgresConnection.query` does not take, to string interpolation of the database name — a fix made earlier inside the spec but never carried to the line itself.
