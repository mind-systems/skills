## Findings

### 1. The `description:` narrows the command's advertised target from "plan/note/task" to a task alone, while the body still handles four target kinds — medium

`:3-11` opens "Read a task, its task spec, and the code the task lands in". The removed `:3` read "Scan a plan/note/task for 'fantasy holes'". The body's target resolution at `:20` did not change and still accepts, in priority order: the file(s) in `$ARGUMENTS` (any file — a plan, a note, a task spec), else the scope under discussion in chat, which it spells out as "a named task, **phase**, or task spec", else all open `- [ ]` tasks of the roadmap. So the frontmatter and the body of the same file now disagree about what this command takes.

This matters more here than it would in an ordinary docstring, and the spec says why: the `description:` is always-loaded contract, not a summary — "a capability missing from it is one the invoking agent may never learn exists" (spec § "The change" item 3), and `docs/skill-description-field.md` describes the field being read as knowledge rather than as a router index, with `:13` naming this very command as an example of an agent acting inside a skill's zone *without invoking it*. The concrete failure is on that path: an agent holding a phase or a plan file, or a user who asks to pin the gaps in a phase, no longer matches the advertised zone, so the always-loaded layer says "task-only" while `:20` would have handled it. Explicit invocation with a path still works — this is a routing narrowing, not a runtime break — which is why it is medium and not critical.

The narrowing was not asked for. The spec required the block to *gain* the three classes and the walk; it required nothing dropped, and its § Verification checks are minimums. Headroom is real: 593 of 1024 characters, so restoring the wider target costs nothing — widen the opening clause to name the plan / task / phase / task-spec targets `:20` actually accepts, keeping the rest of the block as written. Worth keeping in the same edit: the old block's word "guess", which is the phrasing `docs/skill-description-field.md:13` uses for this command's zone and the likeliest word in a user's own request; the new block says only "force invention".
