### Critical Issues

**1. Step 1 — the pinned placement contradicts the dependency the plan itself states.**
The plan says: "Place it after `**Identify the task slug.**` — the slug and `$TARGET_FILE` are both resolved by then — and before `**Read every artifact file found**`."
Ground truth: `$TARGET_FILE` is *not* resolved after the slug sub-block. It is first determined by the **next** sub-block, `**Read the phase's governing spec and phase note.**` (`src/skills/task-rescue/SKILL.md:58-59`: "Determine `$TARGET_FILE` (the same resolution Step 4 determines)"). Nothing earlier in Step 1 touches it.
The consequence is not cosmetic: the same bullet requires the new sub-block to derive the sidecar path from the roadmap file stem (`roadmaps/john-doe.md` → `plans/john-doe/<seq>-<slug>.json`), which is readable only from `$TARGET_FILE`. An implementer following the pinned placement literally inserts an instruction that reads an unresolved variable — and the failure mode the plan itself names ("a sidecar missed by reading the wrong path records exactly the same thing as an absent one — both numbers lost, with no signal") is exactly what results. Note that this rescue's own run is a named-roadmap run, so the wrong branch is the live one, not a hypothetical.
Fix: pin the placement **after** `**Read the phase's governing spec and phase note.**` and before `**Read every artifact file found**`, and drop the now-false justification clause. (The alternative — having the new sub-block resolve `$TARGET_FILE` itself — would duplicate a resolution the file already performs twice and should not be chosen.)

**2. Step 5.7 — `<project>` is specified two contradictory ways in one bullet.**
The destination bullet says `<project>` "is the project name captured in Step 1", and then, one sentence later, "State that **both are resolved at this moment and neither is stored nor cached**." Captured-in-Step-1 and resolved-at-this-moment are mutually exclusive for the same value; "both" has no coherent referent, since under the first reading only one of the two path parts is resolved at write time.
The task spec settles it in the other direction (item 3): "`<project>` from the last segment of `git rev-parse --show-toplevel` in the project being rescued, **both run at this moment** and neither stored or cached" — i.e. Step 5.7 re-runs the project's own git resolution, while the Step 1 capture supplies the `**Project:**` *field of the report body*, not the path. The plan collapses the two roles and lands on the reading the spec rejects.
This is not pedantry about wording: report `03-30-1-…` records that round 3 of the previous run died on precisely this confusion — "the re-resolution named one command where the address needs two, taking the project's name from the very memory the branch exists because it decayed." Leaving it ambiguous re-opens that loop, and it also destabilizes the plan's own verification count (`rev-parse --show-toplevel` ≥ 2, justified as "the project's own name and the skills repo root"), which only holds under the spec's reading if the Step 5.7 resolution is present.
Fix: state that Step 5.7 resolves **both** halves of the address at write time by running `git rev-parse --show-toplevel` in the project being rescued (last segment → `<project>`) and `git -C ~/.claude/skills/task-rescue rev-parse --show-toplevel` (→ skills repo root), and that the Step 1 project fact is what fills the report's `**Project:**` line — then the "neither stored nor cached" sentence is true as written.
