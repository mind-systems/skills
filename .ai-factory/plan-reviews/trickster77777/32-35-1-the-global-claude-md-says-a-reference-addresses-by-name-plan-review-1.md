### Findings

**1. The handoff is told to quote the pinned paragraph — a copy the spec never asks for, into a repository that already loads the original every session.**

The plan's handoff step, item 1: "quote the paragraph so the reader does not have to go find it." The task spec asks for something narrower — the handoff "says: the naming rule is now stated in the global CLAUDE.md, which that project already loads in every session" — and never asks for the text.

The stated justification is the one thing that cannot be true here. The reader of that handoff is an agent working in `tradeoxy_core`, and `~/.claude/CLAUDE.md` resolves to this very file: the paragraph is in that session's system prompt before the handoff is opened. There is nothing to "go find". What the quote does instead is create a second home for the fact this task exists to give a first home, in another git repository, where nothing will maintain it — the global CLAUDE.md § "Grounding claims" is amended by tasks like this one, and a stale copy in `tradeoxy_core`'s handoff 46 will not move with it and nothing will report it. That is one-home-per-fact, and it is the same failure mode the pinned paragraph itself names one register up.

Failure scenario: 35.1 lands; a later task rewords the paragraph (as 34.4 reworded a registry entry); `tradeoxy_core`'s handoff 46 keeps the old wording as a verbatim block quote attributed to the global CLAUDE.md, and the next reader there acts on the superseded text believing it is reading what its own session loads.

Repair: drop the quote requirement, and have the handoff name the rule and its address — the global CLAUDE.md § "Grounding claims", the paragraph opening "A reference addresses by **name**, never by position" — which is a name-address the reader resolves in its own context, and is exactly the form the paragraph prescribes. Naming the opening clause also keeps the handoff checkable if the section grows.

**2. The pinned string is presented in the plan as a Markdown block quote while being called "verbatim as pinned below".**

Inside the first checkbox the paragraph appears as an indented `> …` line, and the instruction above it reads "Insert exactly one new paragraph, verbatim as pinned below". Read literally, "verbatim" and the `> ` prefix contradict each other, and this is a task whose entire deliverable is one byte-exact string.

The mitigation is real but partial: the next paragraph says "Copy the text from the task spec rather than retyping it", and there the string is unquoted. So an implementer that follows the second sentence is safe and one that follows the first is not, in a plan where the first is the one carrying the word "verbatim". The verification checkbox does not close the gap either — "the paragraph appears exactly once" against a whitespace-normalized read would pass on a line beginning `> A reference addresses…` unless the check is run as an equality against the spec's string, which the plan does not say.

Failure scenario: the implementer inserts `> A reference addresses by **name**, never by position. …` into § "Grounding claims"; the paragraph renders as a block quote in the one file every session of every project loads, visibly unlike its seven neighbours, and the plan's own verification passes.

Repair: present the string in the plan the way the file will hold it — a plain paragraph, or a fenced block, not a block quote — and make the verify step an equality against the spec's line rather than a presence count. I applied the plan's edit to a scratch copy of `src/global/CLAUDE.md` this way and it lands clean (below), so the operation is right; only its rendering in the plan is not.
