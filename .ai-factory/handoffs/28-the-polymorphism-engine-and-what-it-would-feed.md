# Handoff — the polymorphism engine and what it would feed

**Processed:** `[ ]` — whoever reads this marks it; a marked handoff is spent.

This file holds a design conversation that arrived at an engine: a load-once philosophy unit that finds where code needed polymorphism and did not get it, and feeds that one question to whichever skill is looking — at an open task or at a closed one.

The user opened on predictions, and on what a spec is for. A spec is built on predictions, and there is no other way to build one: the team tries to predict how the behaviour the docs want will land in code, and the only way to learn whether a prediction was right is to implement it, which is the orchestrator's own job, not the planning pair's. Lately every task had passed cleanly, so by his own reading the method was sound; only this one case had gone wrong from the start, an exception rather than a pattern. Then the observation that opened everything that followed: he saw the generated code following his own working style. He never wrote code all at once. He changed the part he needed, along with the places he assumed depended on it, ran the compiler, fixed whatever it complained about, and learned along the way how the change had actually rippled through the project. And when too many places broke at once, that was itself a signal — either he had bitten off too large a piece of the task, or the code was not yet in a state where the change could land at all. He recognised that same style in how the orchestrator works, and in how the pair's own tasks get written.

The architect's first answer split the claims a spec carries into two sorts, and said only one of them behaves badly. The first sort is claims about the present — this call site exists, this field is typed `string`, this method has no callers. These are not really predictions at all; they are readings. They are checkable right now, cheap to check, and if wrong they die on contact — the very first person who looks finds the truth in seconds. The second sort is claims about a future state some tool will produce: "after this retype, these files will stop compiling." That kind of claim is derivable only by actually doing the thing — and, critically, it already has an oracle that will run regardless of what the spec says, because the compiler runs as part of implementation whether or not anyone predicted its output in advance. The compiler will enumerate its own findings by itself; an enumeration written in prose ahead of time can only ever be correct, incorrect, or stale, and it can never become more useful than what the actual run produces when it happens. That gives a discriminator: write the claim down when it has no cheaper oracle that runs during execution anyway; where an oracle already exists, name the oracle and its coverage, not the list it would produce — a cast that escapes the compiler's own coverage and needs a lint rule as a second oracle is still governed by the same rule, only with a second gate to name instead of one. And a symmetry with a skill already in the family: `test-philosophy` decides what is worth testing on the loud/silent axis — a failure that announces itself needs no test, a failure that doesn't must be caught by one. The same axis, the architect argued, decides what is worth enumerating in a plan: loud failures — a compiler error, a failing test — need only the gate named, never the list of what will trip it; silent ones — a consumer living in another repository, an assertion that quietly stops asserting anything, a doc that becomes a lie and nothing notices — must be enumerated, because for those nothing else will ever catch them. Two further points rode alongside: the user has a signal the orchestrator itself lacks, namely the breadth of what broke, read as a judgement about whether the task was sized correctly; and the whole "change it and see what breaks" style scales exactly as far as its own oracle reaches — which is why a plain retype of a branded id type, where the compiler names every single site that needs attention, goes completely differently from a door contract no compiler checks at all.

The user then corrected the architect, and the correction landed. Eighty compile errors appearing in one test suite is *expected*, not alarming, when a base type is being threaded through a codebase for the first time — the heuristic he'd described was always about *unexpected* breadth, never about an absolute count. A proportional, predictable break says nothing at all about whether a task is too large. Besides — and this mattered — the team could equally well have driven the whole exercise with `grep` and never leaned on compiler errors in the first place; and in fact the pair had never actually reached implementation on this task, so the eighty-odd numbers being discussed came from a reviewer's own probe during planning, not from real work. And underneath that, a deeper objection: if tasks stop predicting the loud problems entirely, the very same stalls simply arrive later, at implementation time, with the compiler doing the complaining instead of the pair's own greps having done it in advance. So the matter is not as clean as it is with tests, where the loud/silent axis settles everything. Still — he said — a good example.

The architect conceded both points, and reframed. With tests, the loud/silent axis decides whether a failure is noticed at all, full stop; here, a compile failure is noticed either way, loud or not, so the real question was never "will this be noticed" but **who pays for noticing it, and when.** The better formulation the architect reached for: **a probe's residue is not a requirement.** The planner had run greps and looked at what broke, and that is genuinely the user's own working style, and it did real, useful work — it is exactly how the shape of the task was learned in the first place, and how the team confirmed the task was doable at all before committing to it. But a probe produces two different things: a conclusion, and a transcript. The conclusion — "compile errors come in exactly three forms, and here is how each one is closed"; "here is the single site that fits none of the three"; "the acceptance command's own coverage already subsumes these directories" — is what actually saves a future implementer from stalling, and it has to survive into the spec. The transcript — a roster of files, each with a reason attached explaining why the reviewer expected it — saves no one at all: the implementer gets the real, authoritative list straight from the compiler when they run it, and all a later reader can do with the transcript is audit it against that list. And here was the one unambiguous part of the whole argument: a transcript **goes stale between the moment it is written and the moment the task actually executes**, and a stale transcript reads as though it were still authoritative, which is worse than if it had never been written at all. Their own transcript had gone stale the moment earlier tasks in the same phase landed — the code moved on, the list did not. An absent list makes the next reader go and look at the compiler themselves; a wrong list makes them believe it, and then argue from something false. So the rule that emerged was narrow, not a ban on prediction as such: never leave inside a durable artifact a snapshot of a state that will already be different by the time the artifact is executed against — leave only the conclusion that was drawn from taking that snapshot.

At this point the user invoked `/task-rescue-audit` — not to run it, but to ask for a view on the skill itself, and on how well it suits the particular class of problem he had in mind: a task trying to untangle spaghetti, where changing one thing makes something ostensibly unrelated fall off elsewhere.

The architect's critique of `task-rescue-audit` opened with what the skill gets right. Its unit of judgement is the sequence of rounds, never an individual fix in isolation — one patch on its own always looks reasonable, three patches in a row is a diagnosis, and only a run of them shows that anything is wrong at all. Its one-sentence root-cause test is a falsifiable gate, and its demand that the sentence be *structural* — an invariant, a derivation rule, a contract, never "don't forget X" — cuts off lazy generalisation before it starts. Its presumption of innocence, and its willingness to return "Mixed, low confidence", both matter, because a detector that shouts at every multi-round task is worse than useless. Its habit of keeping deferred observations out of the causal chain, using them only as corroboration, gives exactly the right weight to "this was seen early and walked past". And its narrative output, rather than a grid, matters because a grid would hide precisely the thing the audit exists to show — that one round's own fix produced the next round's own finding.

Then the blind spots, and the first one lands directly on the very case the user invoked it for. **Its evidence is review prose, not code.** Step 1 instructs the reader to read the plan-reviews and the implementation reviews and reconstruct the causal chain from them — but "change one thing and something unrelated breaks" lives in the *shape of the diff itself*: how many modules it touched, and how far they sit from the file the finding actually named. A reviewer reports what they happened to look at; coupling that nobody looked at leaves no trace anywhere in prose. Worse, the diffs *are* already listed among the skill's own stated inputs, yet Step 1 never actually characterises them — it only asks for "the fix applied", which an agent then paraphrases straight out of the review text rather than out of the diff. Meanwhile Step 4's own discriminators want evidence about the *shape of the code* — growing boolean complexity, workaround-named variables, a flag bolted onto existing logic — while Step 1 is only ever feeding them prose. **Its horizon is a single task.** Spaghetti is a property of a *region* of code, not of a task, and it shows itself across tasks — five tasks in a row each forced to reach into the same file is the real signal, and a single-task audit cannot see that pattern by construction, even though the cheapest possible detector for it — the git history of which files tend to change together — is already sitting there, fully populated, for free. **Two different diseases currently share one name.** "Band-aid accretion" as the skill defines it covers both the case where the *spec* was under-specified, so every round of implementation invented its own local rule, and the case where the *code itself* is tangled, so every fix is forced to reach somewhere the task never named. The symptom looks identical either way: N findings converging on one root sentence. But the remedies are opposite — add a clause to the spec, versus re-partition the region of code — and Step 3's own instruction, to name "a spec clause or design constraint", steers hard toward the first disease only. For the second, the true root sentence is often not a clause at all, but a statement about the *shape* of the code — "module A owns state that module B mutates" — which doesn't fit the test as currently written, so in practice the audit tends to come back with "independent fixes" on exactly the cases it was invoked to catch. **And it is written for implement-phase chains** — "what the implementation did, what the review found" — when a chain can equally be plan-phase, no implementation ever reached, made only of text revisions to a plan; the skill has no account of that shape at all.

Two cheap fixes were proposed at this point in the conversation, and both were superseded later — recorded here anyway, since the thread passed through them. First: capture, per round, how many modules the diff touched, and whether the fix landed outside the module the finding itself named — a fix landing outside its own named module is the fingerprint of coupling, and it is an objective, checkable fact rather than a judgement call. Second: give Step 3 a second, parallel test aimed specifically at the code-side disease — *is there a file present in every round's own fix that is not the actual subject of the task*; if there is, the task was never really about that file, and yet it keeps changing anyway.

The user then named what he actually wanted the skill to find, and it wasn't spaghetti in the generic sense. He wants a skill that finds the smell of "stupid functional programming" showing up where object-oriented code should have been written instead — the case where logic gets split by construction rather than by `if`s. The example he reached for: different states of a layout — backtest, live — should not be sorted out by `if`s scattered through the code; they should work through interfaces, separated architecturally, in space, not in branches. And this is not a rare case, he said — regularly, while writing new code, the pair slides into functional programming, and he has to keep actively watching to keep the layers of meaning separated by proper seams.

The architect located the actual hole this exposed: it sits in the *division of objects between the two skills*. `task-rescue` looks at the *task* — what the spec itself failed to say. An audit of this new kind, by the user's own design, should look at the *code* — which region is shaped in a way that keeps causing tasks to stumble over it. Today's `task-rescue-audit` text sits uncomfortably between the two, reasoning about task quality out of review prose, which just duplicates what `task-rescue` already does. The architect then reached for a checkable reformulation of the smell itself, because "ifs instead of interfaces" invites nothing but a style argument on its own — in TypeScript, an exhaustive `switch` over a discriminated union is legitimate, type-safe, and the compiler actively rewards writing it that way. The sin was never branching as such; it is **where the distinction gets resolved, and how many times.** Branching *before* the object is built is construction — a decision about what to build, followed through by building it. Branching *after*, on a field the already-built object carries, is the smell, because the distinction was never actually resolved at all — it just travels onward as data, forcing every single consumer to re-derive the behaviour that distinction implies, over and over. Signals that follow from this: a repeated discriminator, counted by distinct sites in distinct files rather than by the raw number of `if`s; whether a seam already exists — if an interface is already sitting there and the code still branches on the field anyway, that is a bypassed seam, and it is close to objective; the twin of the same smell living in data — a state machine spread over a boolean and two hint fields instead of one, so every consumer has to reassemble the true state out of a boolean expression of its own; and a tie to rounds — if successive fixes in a rescue chain each add one more branch on the same discriminator, that is convergence by attrition with its root in the code, not in the spec. A counter-signal was named too, to keep the detector from becoming dogma: one exhaustive switch sitting inside an adapter or a factory is not a finding on its own — the thing to count is duplication, never mere presence.

The user corrected this twice. Branching inside a factory is expected and correct — the factory is precisely the one place whose whole job is emitting one invariant of the logic layer or another; the smell is those same comparisons showing up in the code that sits *below* the factory, downstream of construction. And the twin living in data was not a hypothetical for illustration — it was a real finding, already reached once before. Then came the reframe that mattered most: this was never `task-rescue-audit` at all. It is a different skill entirely, one that looks for these problems directly in the code — a facet of prune, perhaps, or a sibling to `/roadmap-test-coverage`, which he already runs before every prune: it walks the completed tasks and looks for surfaces of meaning that have congealed into functional programming.

The architect sketched that skill — a sketch later partly superseded, recorded here as the path actually walked, not as the destination. Its place in the chain would sit right before the prune: the diffs are still fresh at that point, the tasks are still sitting in the roadmap, and new tasks are still cheap to write; after a prune, the trail survives only in git history. Its unit of finding would be neither a task nor a file but a **seam candidate**: one domain distinction, together with the full set of sites that keep re-resolving it. Its evidence would be the code itself — where the distinction gets declared, where it gets read, and for each read, whether that read stands before construction (a factory, a registry, a boundary — all legitimate) or after, on a field of an object that already exists — plus one question that settles roughly half the case on its own: does a type already exist that *could* carry this distinction. Three forms of finding were proposed, each with its own distinct remedy, which is exactly what today's audit lacks the most: *the distinction is unresolved* — branches on the field scattered across modules, cured by resolving it once, at construction, and using polymorphism from there on; *the seam is bypassed* — the interface already exists and a field comparison sits right next to it anyway, a cheap, local cure; and *one container holding two kinds* — a runtime keeping two kinds of slot in one map, with every consumer left to filter the strangers back out, cured not by polymorphism at all but by splitting the store itself. Output would look like `test-coverage`'s own output: candidates, each with its evidence and a proposed shape of cure; the decision to turn any of them into real tasks stays the user's alone; the skill itself never touches code; and its natural neighbour, one step below it in the chain, would be `roadmap-decompose`. Two names were floated for it: `/code-seams`, `/roadmap-seam-audit`. Thresholds were also proposed at this point — at least three reads standing below construction, spread across at least two modules, and the branch has to diverge in *behaviour* rather than merely in a value — and both thresholds were withdrawn in the very next turn.

The user then became decisive, and cut through the whole line of invention. They were, he said, again describing something that has long since been described already — this is polymorphism, plainly. What is actually needed is a skill that checks for polymorphism, because the agent keeps writing code in a functional style regardless, and it is obvious enough that object-oriented programming was not invented for nothing. And to the architect's own standing warning — that whether a seam is genuinely needed depends on how the distinction will go on living *later*, which cannot be extracted from the code alone — the user's answer was that this is easily extractable after all: he extracts it himself, routinely, and he already asks for exactly this kind of judgement at decomposition time, and the pair still keeps sliding into functional programming regardless.

The architect conceded — and named the concession as the same shape of error already made once earlier in this same conversation, over predicting a tool's own output. They had been about to write their own private rulebook for something that already has a name and half a century of literature behind it. The classical anchors, cited rather than re-derived: a conditional written over a *type code*, cured by replacing the conditional with polymorphism; a type-code field itself replaced by subclasses, by state, or by strategy; and, for the data-side twin of the same smell, making illegal states unrepresentable in the first place. The test that followed was then not an invented threshold at all but the open/closed principle, put to the code as one single question:

> To add a third kind, how many places must change?

One place — the factory — is normal; that is precisely what a factory exists for. More than one place, and the distinction is not actually polymorphic at all, whatever the type signatures might suggest. The question needs no thresholds and no sensitivity tuning of any kind: it excludes the factory entirely on its own terms, since that is the single place obliged to change by design; it excludes plain value comparisons entirely on its own terms too, since there is no new kind being added in the first place; and it still catches a bypassed seam from a single offending site, because even though the type already exists, adding a new kind still means going back and editing the branch. The earlier worry about false positives, the architect said, had been an artefact of a bad formulation, never a real property of the underlying problem.

Then, on why the agent keeps sliding into procedural style anyway — and the architect was clear this is not ignorance of object-oriented design, but a **cost gradient**. Adding a branch is a local edit, and its effect is immediately visible, verified on the spot, by the compiler or by a test. Introducing a proper type is non-local by comparison: construction changes, the container changes, every consumer changes along with it. And the pair's whole working discipline pushes hard toward locality at every turn — "do not touch what the task does not name" sits in every work-order they write, reviews punish a diff that spreads, plans enumerate exactly which files are in scope and no more. Under that constant pressure, the branch always wins, because it is the only move available that looks both correct and cheap at the same time. And to make it worse, a discriminated union with an exhaustive `switch` really is idiomatic, modern TypeScript — so the agent has a genuinely legitimate-looking pattern sitting ready to hand, one that really is the right call at a boundary, and wrong the moment it appears below one. The conclusion: the counter-pressure has to be applied at **decomposition**, never at implementation, where the cost gradient always runs against introducing the type. The question "does this task introduce a new kind?" belongs at the moment the task is first written — and if the answer is yes, the task itself must name the seam that is meant to carry it, or the implementer will write a branch instead, and be entirely correct by the letter of the task while doing it.

The user then spoke to fanaticism, and to the closure he had already reached in his own head. Knowing how fanatical agents tend to be once given a rule like this, he expects the whole codebase to end up buried in abstract classes if this isn't handled carefully. He has nothing at all against functional programming where there is genuinely one flow and the simplicity is earned and justified — **but the moment a second invariant appears, that is exactly the place to extract an interface.** And then the closure itself: the skeleton skill is precisely the skill that should already be doing this kind of work. He applies the skeleton lens to tasks that are not yet done; here he found himself reasoning about that same lens applied to tasks that are already *closed* — because analysing open tasks for this is inherently ephemeral, since they have no code yet to examine, whereas looking for polymorphism with the actual code already in hand is, if anything, the easier of the two.

The architect's close was not a quotation of the user but a paraphrase of the common ground the two had actually reached — the classical names had been reached for deliberately, precisely so as not to invent a private rulebook a second time. The user's own restraint rule, the architect said, is sharper than the thresholds the architect had first proposed: count **invariants, not branches**. One flow, and the simplicity stays justified no matter how many conditions it contains; the seam becomes necessary exactly when the second invariant shows up. That is not a threshold at all — it is an **event**, and it has one very pleasant property: it is visible in time. The moment a union gained its second member, an enum its second value, a factory its second branch, is a specific, locatable commit. So the sweeper could look for that moment directly, rather than for "how many places compare `kind`" — when did this kind acquire its second member, and was a seam cut at that moment or not. That framing also bounds the report on its own, for free: one finding per arrival of a kind, never one finding per branch; and it rules out the purely hypothetical case by construction — "there is one kind today, but there might one day be a second" is simply not a finding until that second kind actually exists. On the two homes the same lens could live in: on an open task, the question is "will this introduce a second invariant" — which is a prediction, and predictions, as this very same session had already established from the other side of the conversation, are expensive and go stale. On a closed task, the question becomes "a second invariant has appeared; is it actually carried by a type" — a checkable statement about code, whose evidence already lives in the tree and in the history. The second form, the architect suggested, should feed the first over time, and extracting an interface would then earn a phase of its own — exactly the standing the user says it deserves. One warning was attached to the decomposition-side gate, given the standing fear of fanaticism: if every single task is asked "do you introduce a kind", agents will start inventing kinds purely to look diligent about answering it — so the default answer has to be "no", and the gate must trip only when the task's own text names a second member of an already-existing union, or declares a new union outright, both of which are checkable from the task's own text and the code, never left to open-ended judgement.

The user's final framing is where the conversation seemed to end, before it turned out to have two more turns in it. He sees a new **engine** here — call it "OOP", or call it polymorphism. Just as `test-philosophy` already works as a load-once unit and feeds several other skills from that one place, this same OOP behaviour would feed several skills too. `roadmap-decompose` is possibly one of them, but probably not — decompose, in his own reading, is really about separating meanings out of behaviour, out of the docs, which is a different axis entirely; this new engine runs deeper, somewhere nearer the skeleton skill, or nearer `command-pin-gaps`. Or it could be a wholly new skill that works for both open and closed tasks at once, since its underlying behaviour is one and the same thing in both cases: **finding invariants.**

The conversation continued past that point, and reached two things this file did not yet carry when it was first written. The architect worked out that the question to the code never changes — only the way the region gets chosen does — and that this yields two selectors sharing one lens. One selector takes the seam the roadmap is currently editing: what recently landed work touched. It looks for a kind that gained its second member without a seam being cut, and its evidence is the diff; its trigger is an event read in **time**. The other selector takes a named region instead — a module, a directory, a class, simply "this piece of logic" — where no diff exists at all, and the entry becomes an inventory: enumerate the kinds *declared* there — a union with two or more members, an enum, a boolean field naming a mode, a set of subclasses — and put the same question to each one; the same trigger, now read in **space**. The unit of analysis stays identical either way: a kind, and the sites that resolve it. What this buys is real, and it is what lets the skill be used before any task exists at all — pointed at a region that simply reads badly, with no diff to trigger it and no task yet written, and still get back an answer.

The turn after that went after a tempting counterfactual — had everything been written through abstractions from the very start, none of this would ever have happened — and the architect showed it false, in a specific way. Before the second invariant exists, the *axis* to split on is unknown; an abstraction written ahead of it is a guess about a distinction that has not yet arrived, and if it is wrong, it is wrong in its axis, not merely in its count. The costs on either side of that mistake are not symmetric. A missing seam costs linearly — every new consumer has to re-derive the same behaviour by hand, which is tedious but repairable at any point. A wrong seam costs superlinearly, because everything built below it is shaped by its own choice of axis, and removing a wrong abstraction is dearer than living with a hundred branches ever was. So waiting for the second invariant is not a compromise forced by expedience; it is the engineering-correct move on its own terms. What a university course actually hands over is the catalogue — the patterns, the principles, the named cures — never the *timing*: the moment at which a seam should be cut is absent from the theory entirely, which is exactly why this reads like lab work, where both cases are handed over at once and the axis is already known from the start, and nothing in that setting ever has to notice a moment at all. And the honest correction to the whole counterfactual, reached last, the user's own: this situation was never the product of waiting for the second invariant to show up — it was the product of walking past the second, the third, and the fourth without ever once stopping to ask the question. What had actually gone missing was never earlier abstraction. It was a **moment that forces the question**.

What the conversation actually arrives at, with those two pieces in place, is the conclusion this file was missing — the payoff, not one more snapshot of the reasoning. Three conclusions follow, the first the primary one, the other two kept separate here so neither is lost inside it.

The engine itself: a load-once philosophy unit, built in `test-philosophy`'s own shape — its own file, no I/O of its own, loaded once per chat by whichever skill needs it — holding four things and nothing else. The question: to add a third kind, how many places must change; one place, the site that constructs, is correct on its own terms, and more than one means the distinction was never actually polymorphic at all. The trigger: the arrival of the second invariant — an event, not a count of branches and not a threshold, so that before the second invariant there is nothing at all to do, and after it there is exactly one question to ask. The exemption: the site that constructs is the one place obliged to change, and it is therefore never itself a finding — branching before the object exists is construction; branching after it, on a field the object already carries, is the smell. And the vocabulary: classical, cited rather than re-derived — a conditional over a type code replaced by polymorphism, a type code itself replaced by subclasses, by state, or by strategy, and, for the data-side twin of the same smell, illegal states made unrepresentable. Its default is no finding at all; it only ever fires on the event, never on style.

What the engine really is, stated as the insight rather than as a feature list: a discipline needs a *moment*, not a virtue. "Write through interfaces" is unenforceable on its own, and it breeds exactly the fanaticism the user named and feared — a whole codebase quietly buried under abstract classes, because agents cannot tell when the rule applies and default to applying it everywhere. "At the arrival of the second member, ask one question" is enforceable, bounded, and cheap, and it is exactly `test-philosophy`'s own shape repeated: not "write tests" as a blanket instruction, but a discriminator that says *where*. The mechanism that makes the moment necessary follows directly: at implementation time the cost gradient always favours the branch over the type — the branch is local and verified on the spot, by the compiler or by a test, while the type is non-local and touches construction, the container, and every consumer at once; and the pair's own working discipline reinforces that same gradient rather than fighting it, since every work-order says not to touch what the task does not name, and every review punishes a diff that spreads. So the engine has to be loaded where the decision is still cheap to make — at the tier that writes tasks, and at the tier that inspects code once it exists — and never at the tier that implements, where the gradient has already decided the outcome before the question is even asked.

Why the drift happened at all is a realisation that belongs to the user, and it reframes the whole conversation. He never once mentioned object orientation while the skills themselves were being produced, and he only noticed that fact while asking why the agent does not follow its own principles. Checked against the corpus rather than taken on his word: no skill in the family states a requirement about the *shape* a distinction must take. The family speaks about atomicity, about silent failures, about the closure of a sweep, about citations and their own rot — all of it real, none of it about whether a kind is carried by a type or by a field. So the agent was following the written discipline faithfully all along; what it followed simply never asked the question. That makes this repair additive rather than corrective, and it makes a prediction worth recording on its own terms: put the requirement into the corpus and it will be honoured exactly as faithfully as everything already there is. Stated plainly, because it is the actual answer to "why does the agent keep writing procedural code" — and it replaces the tempting explanation that the agent simply does not know better.

The second addition is the bead map — the engine threaded onto the strings that already exist, plus one new skill. The precedent is exact and already sitting in the tree: `test-philosophy` is a philosophy unit with no I/O of its own, loaded by exactly two skills, `roadmap-test-coverage` and `roadmap-decompose-skeleton`. The new engine threads the same way, and the load-bearing rule that keeps the arrangement honest is that the question is one and the verb differs per consumer — otherwise a shared question quietly becomes a style club instead of a working discriminator.

`roadmap-decompose-skeleton` is the primary bead. Its first lens today decides by judgement alone — a shared type surface between two or more tasks, or a single task whose shape is non-obvious — and the engine replaces that judgement with the event itself: does this task bring a second member to a kind? If it does, the skeleton task *is* the seam. Its own verb is the birth of a task. `command-pin-gaps` takes the bead as a subclass of its own meaning-hole class: a task that adds a branch on a type code already carrying two or more members is a hole, and pin-gaps names it and routes it to its owner rather than repairing it itself, exactly as it already does for every hole whose repair belongs elsewhere. Its verb is report with an owner. The new skill — the "+1" this conversation kept circling — carries the two selectors described above, and it is the only consumer that reads code with no task standing in front of it at all. Its verb is sweep and propose. `task-rescue-audit` takes the bead as the discriminator between the two diseases it currently conflates: where the root-cause sentence turns out to be about the shape of the code rather than a clause of a spec, the engine's own question is the test, and the recommendation turns from amending a spec to re-partitioning a region. Its verb is classify. `aif-architecture` is a candidate rather than a decision: `ARCHITECTURE.md` is the map of space, and a seam once cut is a structural fact that belongs on that map. Its verb would be record, and it is left open. `roadmap-decompose` takes no bead at all, and the reason is worth stating rather than leaving implicit: its subject is separating meanings out of the behaviour the docs describe, while the question about shape needs code in front of it, which decompose never has.

What keeps the beads honest, mirroring `test-philosophy`'s own arrangement exactly: the engine holds the question, the trigger, the exemption, and the vocabulary; each consumer holds when to ask and what to do with the answer; the engine itself never says "extract an interface".
